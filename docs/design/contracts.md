# Contratos internos da Fase 1

Estas interfaces separam `@freecorps/ember-server`, que é TS puro, de `@freecorps/ember-runtime`, que roda em workerd, e de `@freecorps/ember-client`.
Se uma mudança for necessária, atualize este arquivo no mesmo commit.

## SqlDriver (`@freecorps/ember-server`)
Um adaptador mínimo e síncrono. O runtime o implementa sobre `ctx.storage.sql`; os testes usam `node:sqlite` (`@freecorps/ember-server/testing`, fora da entrada principal).
```ts
export interface SqlDriver {
  exec(sql: string, ...params: SqlValue[]): { rows: Record<string, SqlValue>[]; rowsRead: number; rowsWritten: number }
  transaction<T>(fn: () => T): T   // síncrono. Aninhado = savepoint. Lança erro se fn devolver Promise.
}
export type SqlValue = null | number | string | Uint8Array   // sem bigint/boolean: quem converte é o engine
```
- Um statement por `exec`. Parâmetros posicionais (`?` ou `?NNN`). No máximo 100 parâmetros: o engine divide linhas largas.
- BLOBs voltam como `Uint8Array` (o adaptador converte `ArrayBuffer`).

## Valores e JSON (`@freecorps/ember-values`)
- `encodeJson(value): string` / `decodeJson(text): unknown` — JSON canônico com tags: `{"$int64":"…"}` (bigint), `{"$bytes":"<base64>"}`, `{"$float":"NaN"|"Infinity"|"-Infinity"|"-0"}`. Nomes de campo começando com `$` são recusados pela validação, então as tags não colidem. `encodeJsonStable` ordena as chaves (chaves de cache).
- Chave de índice: `encodeKey(values[])` estilo tuplas do FoundationDB. Ordem de tipos `undefined < null < int64 < number < boolean < string < bytes < array < object`; números em ordem total IEEE (`-0 < +0`, NaN canônico depois de `+Infinity`); strings por code point. Comparação por bytes (memcmp). `rangeFor(eq, lower?, upper?)` devolve `[lo, hi)`; `prefixEnd(p) = p ++ 0xFF`; `keySuccessor(k) = k ++ 0x00`.

## Manifesto de schema (`@freecorps/ember-server`)
`defineSchema(...)` expõe `schema.manifest`: JSON serializável.
```ts
type SchemaManifest = {
  version: string            // = hash (sha256 do JSON canônico do resto); é a "versão de schema"
  hash: string
  formatVersion: 1
  schemaValidation: boolean
  tables: Record<string, { idPrefix: string; document: ObjectShape; shard?: { name: string; field: string }; indexes: IndexSpec[] }>
  shards: Record<string, { key: Shape; locationHint?: string }>   // sempre presente (pode ser {})
}
type IndexSpec = { kind: string; name: string; fields: string[]; config?: JSONValue }   // kind "db" = .index()
```
Ele alimenta o DDL, as migrações, o codegen e o cliente offline. `schema.indexKinds` traz os plugins de índice daquele schema (`defineSchema({ ..., indexKinds: [...] })`; `searchIndex` já vem incluído). Não há registro global.

IDs: `<idPrefix>_<ULID>` (o prefixo padrão é o nome da tabela; único por schema).

## Engine (`@freecorps/ember-server`)
```ts
createEngine({ schema, functions, driver, now?, random?, limits? }): Engine   // também é o export default
// functions: { "dir/mod:fn": fn } ou módulos { "dir/mod": { fn } }

interface Engine {
  manifest: SchemaManifest
  migrate(): MigrationReport                 // idempotente; usa _ember_meta; roda em driver.transaction (aninhável); lança MigrationRefused
  planMigration(): MigrationPlan             // dry run
  backfillStep(limit?: number): BackfillProgress   // índices staged, em blocos (padrão 500); chamar até done
  runQuery(name, args, ctx: AuthCtx, opts?: { touched?: Set<string> }): { value: unknown; readSet: ReadSet }
  runMutation(name, args, ctx: AuthCtx): { value: unknown; changes: RowChange[]; scheduled: Job[]; cancelled: string[] }
  runMutationBatch(items: { name; args; ctx: AuthCtx }[]): MutationBatchResult[]   // group commit
  matches(readSet: ReadSet, changes: RowChange[]): boolean
  tableOfId(id): string | undefined
  functionInfo(name): { type: "query" | "mutation" | "action" | "httpAction"; visibility: "public" | "internal"; sensitive?: true; component?: string } | undefined   // componentes: ver "Componentes"
}
type Identity = { subject: string; issuer?: string; exp?: number /* s */; claims?: Record<string, unknown> }
type AuthCtx = { identity: Identity | null }
type ReadSetEntry = {
  table: string; index: string; lo: Uint8Array; hi: Uint8Array /* exclusivo */; kind: string
  filter?: FilterExpr   // kind "db": linhas que falham o filtro antes e depois não invalidam
  data?: unknown        // kinds de plugin (ex.: "search")
}
type ReadSet = ReadSetEntry[]
type RowChange = { table: string; id: string; before: Doc | null; after: Doc | null }
type Job = { id: string; fn: string; args: unknown; runAt: number /* ms */; kind: "mutation" | "action" }
type MutationBatchResult =
  | { ok: true; value: unknown; changes: RowChange[]; scheduled: Job[]; cancelled: string[] }
  | { ok: false; error: { code: string; message: string } }
type MigrationReport = { changed: boolean; fromVersion: string | null; toVersion: string; steps: MigrationStep[]; staged: { table; index; kind }[] }
```
- Queries e mutations são síncronas por dentro: `ctx.db` devolve valores, não Promises. Handler que devolve Promise → erro `AsyncHandler` (e rollback).
- `runMutationBatch`: uma `driver.transaction` com um savepoint por item, mesma ordem dos itens; a falha de um item desfaz só ele e nunca lança. O runtime pode envolver tudo numa transação externa (change log, dedup, jobs).
- `ctx.scheduler.runAfter/runAt` **não** grava nada: os jobs voltam em `scheduled` e o runtime os persiste na própria tabela `_jobs` (coluna `job_id` = `Job.id`, o id devolvido ao handler), na mesma transação. `kind` vem do tipo da função agendada.
- `ctx.scheduler.cancel(id)`: um job agendado pela própria mutation sai de `scheduled`; os demais ids voltam em `cancelled` e o runtime apaga, na mesma transação, o job **pendente** com esse `job_id` (job já rodando/despachado ou id desconhecido: nada acontece).
- `runQuery(..., { touched })`: o engine adiciona ao `Set` cada tabela que a query abriu (`db.query`, `db.get`), inclusive quando ela lança. É o que o runtime usa para reexecutar queries que falharam (ver Protocolo).
- `ctx.now` é fixo por execução; `ctx.random()` usa uma semente por mutation (derivada de `random()`).
- Erros lançados por `runQuery`/`runMutation` são `EmberError` com `code` string: `ValidationError`, `NotFound`, `TooManyReads` (16k linhas), `TooManyWrites` (8k), `DocumentTooLarge` (2 MB), `SchemaError`, `MigrationRefused`, `IndexNotReady`, `FunctionNotFound`, `InvalidFunction`, `AsyncHandler`, `QueryError`, `InvalidCursor`, `FileNotFound`, `FileInUse`, `StorageError`, `OfflineUnsupported` (só em execução local, ver "Offline"). Outros erros (do usuário) viram `code: "Error"` no batch.
- Visibilidade (`internal*`) é checada pelo runtime via `functionInfo`.
- Chaves de índice: coluna BLOB `_k_<índice>` com `encodeKey([campos..., _creationTime, _id])`. `by_id` é `encodeKey([_id])`; `by_creation_time` é `[_creationTime, _id]`.
- Kinds de índice que não são `db` (busca, por exemplo) decidem o próprio matching pelo plugin (`matchesChange`). Um kind com `debounceTableWrites: true` (busca: o bm25 depende da tabela inteira) tem as escritas na tabela que `matchesChange` rejeita reportadas como match "loose".
- **Agregados materializados** (`defineTable(...).aggregate(name, { by: [campos], count?: true, sum?, min?, max? })`): é um index kind embutido (`kind: "aggregate"`, `fields = by`, `config = {count, sum, min, max}`), então o planner cria, apaga e faz staging como qualquer índice.
  - Tabelas: `<tabela>__<nome>` (`key BLOB PRIMARY KEY` = `encodeKey(valores do grupo)`, `count INTEGER`, `v TEXT` = `encodeJson({sum, min, max})`, `WITHOUT ROWID`) e, com min/max, `<tabela>__<nome>__mm` (`key` = `encodeKey([nº do campo, ...grupo]) ++ encodeKey([valor])`, `n` = multiplicidade): remover o min/max atual custa um seek.
  - Mantidos pelo engine na transação da mutation (insert/patch/replace/delete/increment): um read + um upsert por grupo tocado; grupo com `count = 0` some. Somas: `number` → float; `int64` → bigint. Os writes contam no limite de 8k.
  - Leitura: `ctx.db.aggregate(table, name).get([...grupo])` → `{count, sum, min, max}` (grupo vazio = `count: 0`, somas 0, min/max `null`) é uma busca por chave primária; `.range(q => q.eq(...).gt(...), {order?, limit?})` → linhas com `group`. Antes do backfill terminar: `IndexNotReady`.
  - Reatividade: cada linha de agregado que muda vira um `RowChange` da pseudo-tabela `"<tabela>__<nome>"` (docs `{_id: "agg_<hex da chave>", g0..gN, count, sum, min, max}`); as leituras gravam ranges `db` no índice `by_group` (campos `g0..gN`) dessa pseudo-tabela. `readSetFields(manifest, table, index)` resolve os dois casos para `engine.matches` e `createMatchIndex`. Um agregado que volta ao valor anterior na mesma mutation não gera change.
  - Backfill (staged): escritas ao vivo ignoram linhas na janela `(cursor, until]`; `backfillStep` agrega cada linha da janela uma vez.
- **`ctx.db.sql`** (queries e mutations, somente leitura): tag `` ctx.db.sql`SELECT ...` `` (linhas `unknown`) ou `ctx.db.sql(v.object({...}))`...`` (linhas convertidas — 0/1 → boolean, TEXT → int64 — e validadas; falha → `ValidationError`).
  - Valores do template são sempre parâmetros `?`; identificadores só via `ctx.db.sql.id(nome)` (`[A-Za-z_][A-Za-z0-9_]*`, entre aspas). Placeholders escritos à mão (`?`, `:x`, `@x`, `$x`) e valores dentro de literais são recusados.
  - Validação por tokenizer (fora de strings e identificadores entre aspas): um único statement começando com `SELECT` ou `WITH`; recusa `INSERT/UPDATE/DELETE/REPLACE/CREATE/DROP/ALTER/ATTACH/DETACH/PRAGMA/VACUUM/REINDEX/ANALYZE/BEGIN/COMMIT/ROLLBACK/SAVEPOINT/RELEASE/TRIGGER/RETURNING/INTO/EXPLAIN`, `load_extension()` e funções `pragma_*`. Cada fonte de `FROM`/`JOIN`/vírgula precisa ser tabela do schema (sem diferenciar maiúsculas), CTE do statement, ou `json_each`/`json_tree`; nome qualificado (`main.t`), tabelas internas (`_*`, `sqlite_*`, `t__idx`) e outras table-valued functions → `QueryError`.
  - Colunas são o layout físico (escalares de primeiro nível; o resto em `_json`). Reatividade por tabela: grava `[lo, hi)` cheio de `by_creation_time` de cada tabela referenciada (e as põe em `touched`). `rowsRead` do cursor conta no limite de 16k.
- **`ctx.db.increment(id, field, delta)`** (mutations): soma `delta` (number, ou bigint para int64) a um campo de primeiro nível, lido e escrito pelo engine; campo ausente = 0; devolve o novo valor. É um patch comum (validação, agregados, change). Contador shardeado (escrita sem conflito entre mutations) fica para um componente.
- `createMatchIndex<K>(schema): MatchIndex<K>` — índice de read sets para muitas inscrições: `set(key, readSet | null, tables?)`, `delete(key)`, `match(changes) → { exact: Set<K>; loose: Set<K> }`. Ranges `db` ficam numa estrutura de intervalos por `(tabela, índice)` (array ordenado por `lo` + segment tree de `max(hi)`, buffer de inserções e tombstones, rebuild preguiçoso); entradas de plugin seguem por `matchesChange`, agrupadas por tabela; `readSet: null` com `tables` = casa qualquer mudança nessas tabelas. `exact` é exatamente o conjunto em que `engine.matches` é true (sem falso negativo; o fuzz compara os dois).

## Crons (`@freecorps/ember-server`)
`crons.ts` exporta por padrão `cronJobs({ shard?, tz? })` (builder: `.cron(name, schedule, fn, args?, opts?)`, `.interval`, `.hourly`, `.daily`, `.weekly`, `.monthly`) ou um `CronDef[]`:
```ts
type CronDef = { name: string; schedule: string; tz?: string; shard: string; fn: FunctionReference<"mutation" | "action"> | string; args?: unknown; kind?: "mutation" | "action" }
```
`cronList(x)` normaliza o export. O runtime resolve `fn` para o nome e `kind` para o tipo da função (default `mutation`, `action` se a função for uma action).
- Índices staged: o runtime chama `backfillStep(500)` um bloco por turno de alarm (reagendando o alarm até `done`); o índice fica consultável quando termina (antes disso → `IndexNotReady`).
- Tabelas internas: `_ember_meta`, `_ember_indexes` (engine) e `_jobs`, `_ember_migrations`, `_ember_rt_meta`, ... (runtime). O planner ignora tudo que começa com `_` ou `sqlite_`, e as tabelas-sombra do FTS5.

## Protocolo WS v1 (`@freecorps/ember-runtime` ⇄ `@freecorps/ember-client`)
Frames JSON (valores em `encodeJson`); o binário fica para depois. Ping e pong são as strings literais `"ping"` e `"pong"`, para a auto-response funcionar.
Cliente → servidor:
- `{t:"hello", clientId, token?, protocol:1, features?: string[]}` — v1.1: features opcionais; o servidor ignora as que não conhece
- `{t:"sub", qid, fn, args, resume?:{version, epoch, ik?}}` — `ik` só com a feature `"ident"`
- `{t:"unsub", qid}`
- `{t:"mut", mid, fn, args}`
- `{t:"auth", token}` — `token: null` faz sign-out: o socket passa a anônimo e todas as suas subscriptions são reavaliadas (novo `snap`)

Servidor → cliente:
- `{t:"ready", shard, version, epoch, features?}` — as features do hello que o servidor fala (`"rowdiff"`, `"ident"`); ausente = nenhuma
- `{t:"snap", qid, version, value, ik?}` — `ik` só com a feature `"ident"`
- `{t:"snap", qid, version, unchanged:true}` — sem `value`: resposta a um `resume` bem-sucedido (o valor do cliente continua válido)
- `{t:"patch", version, changes:[{qid, value} | {qid, diff}], mids}` — um frame por versão confirmada, cobrindo todas as queries que mudaram. `mids` (sempre presente, pode ser `[]`) são os `mid`s **deste socket** cujos efeitos estão nessa versão, para o cliente descartar os updates otimistas correspondentes de forma atômica; o `mres` de cada um vem depois
- `{t:"mres", mid, ok:true, value, version} | {t:"mres", mid, ok:false, error:{code, message}}`
- `{t:"err", code, message, qid?}`
- `{t:"authExpired"}`

Regras:
- **Feature `rowdiff` (v1.1).** Sem ela, `patch` leva o valor inteiro. Com ela, quando o valor anterior que o socket recebeu (sucesso) e o novo são arrays de objetos com `_id` string distintos, e o diff é menor em JSON, o change é `{qid, diff:{remove:[ids], upsert:[docs], at?:[índices], order?:[ids]}}` (`rowDiff`/`applyRowDiff` de `@freecorps/ember-values`). Aplicar: (1) tira `remove`; (2) um doc de `upsert` cujo `_id` ainda existe é trocado no lugar, os outros são "inseridos"; (3) inseridos vão para o fim, em ordem, ou, com `at` (índice final crescente de cada inserido), entram nessa posição; (4) com `order` (todos os ids), reordena. Doc que muda de posição vai como removido + inserido (mínimo de movimentos, pela maior subsequência crescente); `order` só quando é menor. Senão, `{qid, value}`. O cliente aplica no valor confirmado (as camadas otimistas são reaplicadas por cima); se o diff não encaixa, manda `unsub` + `sub` sem `resume` e recebe `snap` completo. Medido (lista de 500 docs, 1 mudança, frame `patch` inteiro): update 69 794 → 203 bytes, insert 69 903 → 199, delete 69 764 → 128 (≈ 340–545×).
- Dedup de mutation por `(identity, clientId, mid)`. **Janela: o resultado de um `mid` fica guardado no mínimo 7 dias (`DEDUP_RETENTION_MS`) e no máximo 14**, também depois de reinício ou hibernação do DO (gravado na mesma transação dos efeitos). Um reenvio dentro da janela devolve o resultado guardado (mesmo `value`/`version`) sem rodar de novo; depois dela, o `mid` conta como novo. Guardado em tabelas de geração `_ember_dedup_<n>` (`WITHOUT ROWID`, chave primária `(identity, client_id, mid)`, sem índice secundário): grava na mais nova, procura nas duas mais novas; a manutenção abre uma geração nova quando a atual faz 7 dias e apaga a anterior com `DROP TABLE` (não custa linha escrita). A tabela antiga `_ember_dedup` (runtime < 3) vale como geração 0 até a primeira rotação. Troca: 1 linha por mutation em vez de 3 (linha + índice `at` + `DELETE` da limpeza); a janela passa de exatos 7 dias para 7–14 dias. Uma fila offline que reenvia depois de mais de 7 dias pode rodar a mutation de novo, como antes.
- **Feature `ident` (v1.1).** Com ela, todo `snap` com valor leva `ik` (marca de 53 bits da identidade sob a qual foi calculado) e o cliente devolve, em `resume.ik`, a marca do valor que tem. `unchanged` só sai se `ik` é a marca da identidade atual do socket; sem `ik`, ou com outra, vai `snap` completo. Assim o shard não grava nada por snapshot. Sem a feature (clientes antigos), o shard grava a identidade de cada snapshot em `_ember_sub_ident` como antes. A marca não é segredo: forjá-la só faz o próprio cliente ficar com um valor que já tinha. Na reconexão com pipelining (`sub` logo depois do `hello`, antes do `ready`), o cliente já manda `resume.ik` quando tem a marca (só um servidor com `ident` daquela época a deu); se o `ready` não confirma `ident` (runtime revertido, que recusa o campo como `bad_frame` sem `qid`), o cliente reenvia essas subscriptions sem a marca e não reporta essas recusas.
- Subscriptions de um socket ficam no anexo do socket (`serializeAttachment`, até 16 KB), que sobrevive à hibernação e não custa linha escrita; as que não cabem vão para `_ember_subs`. Ao acordar, o shard refaz o registro pelos dois.
- Só funções `public` do tipo certo podem ser chamadas por clientes (WS e HTTP), via `engine.functionInfo`: função interna ou inexistente → `FunctionNotFound` (não revela que existe); tipo errado → `InvalidFunction`. Funções `internal*` rodam só pelo scheduler/crons.
- `sub` cuja query falha continua registrada (estado "errored"): o servidor manda `err` com `qid` e, como ela não tem read set, a reexecuta só depois de commits que tocam tabelas que a função sabidamente lê (as que essa execução abriu antes de falhar + as que qualquer execução anterior da mesma função leu), e quando um índice staged fica pronto; o primeiro sucesso chega como `patch`. Uma query que falha antes de ler qualquer tabela só volta a rodar por re-`sub`, `auth` ou índice pronto. Reenviar `sub` com o mesmo `qid` de uma sub errored a reexecuta (não é `duplicate_qid`).
- Matching: o shard mantém um `createMatchIndex` sobre as queries inscritas; um commit reexecuta só as chaves `exact`.
- Busca (PLAN §4): reexecução **imediata** quando a mudança pode alterar o conjunto de resultados (linha que está nos resultados, ou texto antes/depois com um termo da busca passando nos filtros, ou um range `db` da mesma query). **Com debounce** quando a escrita só toca a tabela pesquisada (match "loose": pode mudar a ordem bm25): uma reexecução no máximo `reactivity.searchDebounceMs` (padrão 2000 ms; `0` = imediato) depois da *primeira* escrita loose, sem ser empurrada por escritas seguintes — a ordem nunca fica mais velha que isso. O patch do debounce leva a `version` atual e só sai se o valor mudou; uma reexecução imediata cancela o debounce pendente daquela query.
- Token expirado em socket aberto: na hora do patch o servidor checa o `exp` da identidade do socket; se expirou, **não** manda patches nem `err` dessas subscriptions e manda `{t:"authExpired"}` uma vez (até o próximo `auth`). Depois de `auth` com token novo, as subscriptions recebem `snap` como sempre.
- `resume` só responde `unchanged` se o valor do cliente foi calculado sob a mesma identidade do socket atual (com `ident`: `resume.ik`; sem: o último snapshot daquele `(clientId, qid)` em `_ember_sub_ident`); senão vai `snap` completo. O change log é um anel de `changeLogVersions` (padrão 256) posições em `_ember_changes` (`slot = version % N`, um upsert por commit; a entrada mais nova também guarda a versão do shard).
- Frame `sub`/`mut` que chega depois do `exp` do token **não** roda como anônimo: o servidor responde `authExpired` e, para `mut`, `mres ok:false code:"auth_expired"` (para `sub`, `err` com `qid` e `code:"auth_expired"`), e descarta o frame. O cliente manda `auth` com um token novo.
- Erros de usuário em queries/mutations usam `code:"Error"` (os `EmberError` mantêm o próprio `code`).
- Um shard por socket: `/ws?shard=<tipo>:<chave>`.
- HTTP one-shot: `POST /api/query`, `POST /api/mutation` e `POST /api/action` com `{fn, args, shard}`. Resposta `{ok:true, value, version}` (`version` só em query/mutation) ou `{ok:false, error:{code, message}}` (HTTP 400; 401 para token inválido).
- Actions rodam no Worker. `ActionCtx` (`@freecorps/ember-server`): `runQuery/runMutation/scheduler` no shard da chamada (`ctx.shard`), `ctx.onShard(s)` para outro shard, `runAction`, `auth.getUserIdentity()`, `env` (bindings) e `now`. Cada chamada é um RPC ao DO do shard (sua própria transação), com a identidade de quem chamou; actions podem chamar funções `internal*`. `ctx.scheduler` grava direto no `_jobs` do shard (não é transacional) e `cancel(id) → boolean`. Erros de shard viram `ActionCallError` com o `code` original.
- Jobs de action: `ActionJobMessage = { shard, jobId: string, fn, args, attempt, lease?: true }` vai para a Queue `EMBER_ACTIONS` (o Worker exporta `queue()`). Sem Queue (e sem `dispatchAction`), ou com `action({ dispatch: "shard" })`, o próprio shard roda a action no turno do alarm.
  - **Lease** (`lease: true`): o shard não apaga a linha ao despachar. Ela fica `dispatched` com `run_at = agora + lease` (`action({ leaseMs })`, senão `scheduler.actionLeaseMs`, padrão 5 min, mínimo 1 s por action). O consumer chama `Shard.claimActionJob(shard, jobId)`: `{ run: true }` move para `claimed` com um lease novo; `{ run: false }` (cancelado, já rodado pelo shard, outra entrega) faz `ack()` sem rodar. Depois de rodar, `Shard.settleActionJob(shard, jobId, error | null)`: sucesso apaga a linha; falha conta a tentativa e volta a `pending` com backoff (ou `failed` após `maxAttempts`), como qualquer job. O consumer sempre faz `ack()`; só refaz a entrega (`retry()`) quando o shard está inacessível no claim.
  - **Lease vencido:** o alarm pega jobs `pending`, `dispatched` e `claimed` vencidos; um `dispatched`/`claimed` vencido roda no próprio shard (`running`), e uma entrega atrasada não acha o que reivindicar. Entrega pelo menos uma vez: se o consumer rodou mas não conseguiu informar, o shard roda de novo ao vencer o lease.
  - `ctx.scheduler.cancel` e `cancelJob` removem jobs `pending` ou `dispatched` (ainda não reivindicados).
  - Mensagens sem `lease` (de um runtime anterior) seguem o comportamento antigo: `ack()` em sucesso, `retry()` em falha.
- Location hint: o Worker (e o System) cria os stubs com `locationHint` = `shards[kind].locationHint` do manifesto (`defineShard`) ou, na falta, `env.EMBER_LOCATION_HINT`. Só vale na criação do DO.

## Auth (`@freecorps/ember-runtime` ⇄ `@freecorps/ember-auth`)
```ts
interface EmberAuthHook {   // emberAuth(...) e remoteAuth(...) de @freecorps/ember-auth/worker satisfazem
  verify(token: string, opts?: { sensitive?: boolean }): Identity | null | Promise<Identity | null>
  fetch?(request: Request, env): Response | null | undefined | Promise<...>   // /api/auth/*; tentado antes do 404
}
```
- `mutation({ sensitive: true, ... })` / `action({ sensitive: true, ... })` (query recusa). Com token, o Worker verifica com `{ sensitive: true }` (sessão no DO `Auth`); sessão encerrada → 401 `unauthenticated` mesmo com JWT ainda válido. Sem token, roda anônimo. No WS o shard guarda o token do socket (attachment) e reverifica a cada `mut` sensível: `mres ok:false code:"unauthenticated"` (sessão encerrada) ou `"reauth_required"` (token não disponível). Chamadas internas (actions → shard) não reverificam.
- Entry gerado com `ember/auth.config.ts`: `const auth = emberAuth(cfg, { project, onUserChange: outbox.onUserChange }); export const Auth = outbox.wrap(auth.Auth); createEmberWorker({ ..., auth })`. Com `ember.json` `auth.from` (SSO): `remoteAuth({ from })`, sem DO `Auth`. `auth.from` aceita a URL do projeto de identidade (barra final e caminho aceitos) **ou o nome** (`"<projeto>"` / `"<projeto>/<env>"`): o `ember deploy` resolve pelo registro (`environments.url`; env = o dado, senão o mesmo nome do env do deploy, senão `prod`, senão o único; ambíguo/sem URL → erro), gera o entry com a URL e grava `auth_links(project, env, identity_project, identity_url)`. Fora do deploy (ex.: `ember dev`) um nome é recusado com a instrução de usar a URL.
- Outbox de perfil: `onUserChange` grava `_ember_outbox` no SQLite do DO `Auth` e arma o alarm; o alarm entrega em ordem `internal.users.sync({ event: "create"|"update"|"delete", user, key })` (datas em ms, campos privados removidos) no shard `auth.syncShard` (padrão `global:main`), com backoff e `dead = 1` após `maxAttempts` (10). Só grava se `users:sync` existir (internalMutation). Dedup: `Shard.mutation(shard, fn, args, identity, internal, { dedupKey })` guarda só resultados `ok` nas tabelas de dedup do shard (mesma janela de 7–14 dias das mutations do WebSocket).
- **Lacuna de crash do outbox (fechada):** o Better Auth roda `databaseHooks.*.after` depois do commit da escrita do usuário; um DO `Auth` que morre entre os dois perdia a mudança. Agora `@freecorps/ember-auth` instala, a cada boot (com `onUserChange`), triggers `AFTER INSERT/UPDATE/DELETE` na tabela de usuário que gravam `_ember_user_journal(seq, user_id, event, at, data)` **na mesma transação** da escrita (`userJournalDDL`: `DROP` + `CREATE` de cada trigger numa transação a cada boot, para o corpo acompanhar colunas novas e mudanças de tipo, que não mudam o fingerprint do schema; no delete, `data` = a linha antiga como o hook a veria: chaves de campo, datas em ms, booleanos JSON). O hook grava a linha do outbox e apaga a linha de journal correspondente (a mais antiga com o mesmo `user_id` e `event`) num único `transactionSync`. Uma linha de journal com mais de `journalGraceMs` (padrão 60 s) é de um hook que nunca rodou (crash, ou plugin escrevendo por fora dos hooks): o alarm a converte em linha de outbox com o estado **atual** do usuário (`Auth.userForSync(id)`; delete: `data`), chave `<event>:<id>:recovered:<seq>`. O construtor do `Auth` embrulhado arma o alarm quando há journal pendente (a próxima ativação do DO depois do crash: qualquer requisição de auth). Ordem: linhas recuperadas entram no fim da fila, mas levam o estado atual, então `users.sync` (upsert) converge.
- Deploy: `Auth` em `exports` + binding `AUTH`, `nodejs_compat`; `EMBER_AUTH_URL` (plain_text: `auth.url` ou workers.dev); `EMBER_AUTH_SECRET` gerado só se o Worker ainda não tem esse secret (depois fica por `keep_bindings`); `EMBER_AUTH_JWKS` = `GET <url>/api/auth/jwks` gravado via `PUT .../secrets` se ainda não existe (cria um deployment).

## Admin / status (`@freecorps/ember-runtime`)
`GET /api/_ember/status?shard=<s>&shard=...` (padrão `global:main`, até 50) com `Authorization: Bearer <EMBER_ADMIN_TOKEN>` (secret do Worker; sem ele → 403 `admin_disabled`; token errado → 401). Acordar o shard roda a migração dele. Resposta:
```ts
{ ok: true, expectedVersion: string, shards: Array<{
  shard: string; expectedVersion: string; schemaVersion: string | null
  ready: boolean                      // schemaVersion === expectedVersion, sem índice staged, sem recusa
  staged: { table; index; kind; cursor: number; until: number }[]   // faltam as linhas (cursor, until]
  migrationError: { at; fromVersion; toVersion; code; message } | null   // a última tentativa para expectedVersion foi recusada
  lastMigrationError: (mesmo tipo) | null                                 // histórico
  version: number; databaseSize: number }> }
```
- Migração recusada (`MigrationRefused` ou falha de DDL) no boot: a transação volta atrás, o shard fica no schema antigo, registra a tentativa em `_ember_migrations(at, from_version, to_version, ok, code, message)` e recusa trabalho com esse erro (`mres`/`err`/HTTP com `code: "MigrationRefused"`, jobs e backfill parados) até um deploy que migre. Cada boot (deploy novo = isolate novo) tenta de novo.
- `ember deploy --wait [--shard s ...]` faz polling desse endpoint (sempre `global:main` + `--shard`) até todos `ready`; falha alto (`MigrationRefusedError`) se algum tiver `migrationError`. O deploy sobe `EMBER_ADMIN_TOKEN` (variável de ambiente local ou `--admin-token`) como `secret_text` e manda `keep_bindings: ["secret_text","secret_key"]`.

## Secrets e vars (`ember env`) — PLAN §13
- **Secrets** = secrets de Worker (`secret_text`) de `ember-<project>-<env>`, pela API de Workers (`PUT/GET/DELETE /workers/scripts/<w>/secrets`). Um `PUT` publica uma versão nova na hora; todo upload do `ember deploy` leva `keep_bindings: ["secret_text", "secret_key"]`, então sobrevivem aos deploys. Antes do primeiro deploy: erro com o próximo passo. Deploy gradual em curso: `set` e `rm` dão erro (a mudança cairia numa versão só).
- **Vars** = `environments.<env>.vars` no `ember.json` (texto, versionado, `plain_text` no próximo deploy). Um nome é secret **ou** var: `ember env set` recusa o outro tipo e o deploy falha se os dois existirem.
- **Nomes:** `[A-Za-z_][A-Za-z0-9_]*`; `EMBER_*` é do Ember (deploy, `ember keys rotate`): listados como "managed", nunca alterados nem revelados.
- **Valores** de secrets nunca vêm da linha de comando (histórico do shell): stdin, prompt oculto ou `--from-env VAR`. Vars (não secretas) recebem o valor na linha de comando com `--var`, ou também por `--from-env VAR`; os dois juntos é erro. Flags que o subcomando não usa (`list --var`, `get --var`, `set --local`, `--url`/`--admin-token` sem `--reveal`...) são erro, não ignoradas. A CLI não imprime, não loga e não grava valores. `get` diz só onde o nome está; `--reveal` lê um secret pela própria Worker: `POST /api/_ember/env/reveal { name }` (admin token; recusa `EMBER_*` e `BETTER_AUTH_SECRET` — nome legado do secret do auth — com 403 `managed`; 404 se não existe; `cache-control: no-store`). Vars com `--reveal` vêm do `ember.json`.
- **Dev:** `.dev.vars` ao lado do `ember.json` (sintaxe dotenv: `export`, comentários, aspas simples/duplas, escapes em aspas duplas, multilinha), relido a cada rebuild do `ember dev` e passado como vars ao Miniflare; `EMBER_*` ali é ignorado com aviso; aviso se o git não ignora o arquivo. `ember init` acrescenta `.ember/` e `.dev.vars*` ao `.gitignore`.
- **Por que não Secrets Store** (pesquisado em 2026-11, beta aberto): um store por conta e 100 secrets por conta, divididos entre todos os projetos e ambientes (§21); leitura assíncrona `await env.X.get()` (bibliotecas que esperam `env.X` string, como o Better Auth, precisariam de adaptador); secrets de produção inacessíveis no dev local. Reavaliar quando o limite subir: o binding seria `{ type: "secrets_store_secret", name, store_id, secret_name }`.

## Turnstile no auth (`ember.json` `auth.turnstile`) — PLAN §13
- `auth.turnstile: true | { endpoints?, expectedAction?, allowedHostnames? }` (por ambiente em `environments.<env>.auth`; `false` desliga). Precisa de `ember/auth.config.ts`; com `auth.from` (SSO) é recusado (o captcha fica no projeto de identidade).
- O entry gerado passa `turnstile` ao `emberAuth`, que roda o `onRequest` do plugin `captcha` do Better Auth (`provider: "cloudflare-turnstile"`) **na Worker, antes do hash/verify de senha**: um pedido recusado não custa scrypt e não chega ao DO `Auth`. O token é de uso único, então só há essa verificação (o plugin não entra nas opções do DO; um `captcha()` no `auth.config.ts` junto com `auth.turnstile` é recusado).
- Rotas padrão do Better Auth: `/sign-up/email`, `/sign-in/email`, `/request-password-reset` (`endpoints` substitui). Toda rota configurada exige o token em qualquer método (um endpoint GET também); só preflight CORS (`OPTIONS`) passa. Cliente: header `x-captcha-response`. Respostas: 400 `MISSING_RESPONSE`, 403 `VERIFICATION_FAILED` (inclui `expectedAction`/hostname), 500 `UNKNOWN_ERROR` (siteverify fora). IP do cliente: `cf-connecting-ip` (salvo `advanced.ipAddress.ipAddressHeaders`).
- Secret: `TURNSTILE_SECRET_KEY` (`ember env set`; `.dev.vars` no dev). Sem ele, as rotas protegidas respondem 500 `CAPTCHA_NOT_CONFIGURED` (fecha) e o motivo vai para o log; `ember deploy` e `ember dev` avisam. Chaves de teste da Cloudflare: secret `1x0000000000000000000000000000000AA` (passa), `2x…AA` (falha), `3x…AA` (token já usado), token `XXXX.DUMMY.TOKEN.XXXX`.

## PITR / `ember restore` (`@freecorps/ember-runtime` restore.ts ⇄ `@freecorps/ember-cli` restore.ts)
- **Bookmarks próprios** em `_ember_bookmarks(id, at, bookmark, reason)` de cada shard (R6: `getBookmarkForTime` é grosseiro), via `getCurrentBookmark()`:
  - `deploy:<versionId>`: no primeiro boot sob uma versão nova do Worker (binding `version_metadata` `EMBER_VERSION`), **antes** da migração e de qualquer requisição do código novo (meta `deploy_version`). Vale também para o **primeiro boot de um shard novo** (o estado "antes" é vazio). Se o bookmark falha, grava `deploy-missed:<versionId>` com `bookmark = ''`: alvos `deploy:` recusam esse shard em vez de passar por cima do que ele escreveu;
  - `migrate` (depois de migrar), `hourly` (manutenção horária, só enquanto o shard está ativo), `manual:<label>` (`POST /api/_ember/bookmark`), `pre-restore:<id>`, `undo:<id>`, `restore:<id>`.
  - Linhas com mais de 30 dias saem na manutenção (é a janela do PITR). `id` cresce na ordem de gravação, inclusive entre linhas do timeline desfeito reimportadas por um restore.
- **Admin** (mesmo `EMBER_ADMIN_TOKEN`): `GET /api/_ember/bookmarks?shard=` → `{ok, shard, now, retentionMs, bookmarks}`; `POST /api/_ember/bookmark {shard, label?}` (501 `pitr_unavailable` sem PITR); `POST /api/_ember/restore {shard, bookmark, label?}` → `{ok, shard, restoredTo, undo, version, epoch, schemaVersion}`. Erros: 400 `bad_bookmark`; 409 `restore_in_progress`; 501 `pitr_unavailable` (workerd local); 500 `restore_failed` (nada mudou); 500 `restore_unconfirmed` (agendado, ainda não confirmado; a mensagem traz o undo).
- **Máquina de estados do restore** (um restore = um `nonce`; nada dentro do shard sobrevive ao restore):
  1. `restorePrepare` (instância antiga): recusa se esta instância já agendou um (`restore_in_progress`); grava `pre-restore:<id>`; copia as linhas de bookmark; grava a meta `restore_pending = <nonce>`; registra o restore no **diário do System DO** (`_ember_restores`); só então `onNextSessionRestoreBookmark(bm)` (devolve o **undo**: o estado imediatamente antes de o restore aplicar, incluindo escritas entre prepare e o restart). Falha antes de agendar → apaga a marca, grava o resultado `failed` (ver 3) e tira a entrada do diário. Depois de agendar, grava o undo no diário (melhor esforço). Devolve `{undo, rows, nonce, instance}`.
  2. `restoreAbort`: `ctx.abort()`; a chamada falha por desenho, então o erro dela não diz nada. O próximo restart (abort, eviction ou deploy) aplica o restore.
  3. `restoreFinish(info)` (instância nova). Cada `nonce` tem um **resultado** na meta `restore:<nonce>` (`failed` | `applied` | `done`), gravado depois da marca (o banco restaurado nunca o tem) e nunca apagado; ele é lido primeiro: `failed` → `restore_not_scheduled` (para sempre: nenhuma chamada posterior desse `nonce` relata sucesso); `done` → mesma resposta, nada muda; `applied` → refaz os passos não transacionais (abaixo). Sem resultado: marca deste `nonce` presente e mesma `instance` → `restore_not_applied` (não reiniciou: o Worker aborta de novo); marca presente e outra `instance` → reiniciou sem restore: apaga a marca e grava `failed` na mesma transação, resposta `restore_failed`, dados intactos. Marca e resultado ausentes: a marca é mais nova que qualquer bookmark que se possa restaurar, então **isso prova que o restore aplicou** (só porque nenhum caminho apaga a marca sem gravar um resultado). A conclusão tem três passos, cada um idempotente, e só o último grava `done`; um retry (Worker ou alarm do System) depois de uma queda em qualquer ponto refaz o que falta:
     1. transação: apaga marca obsoleta de outro restore (restaurar um undo traz a marca daquele restore; não a de um restore agendado por esta instância), reimporta as linhas que o restore desfez (`INSERT OR IGNORE` por `id`: o banco restaurado é um prefixo), grava `undo:<id>` (se o undo é conhecido), **troca o `epoch`** (clientes com `resume` recebem `snap` completo) e grava `applied`;
     2. **fecha (1012) todo socket** (pode ter feito `resume` contra o epoch antigo, com versões que o timeline novo reusa; fechar de novo num retry é inofensivo), rearma o alarm e dispara o outbox (jobs, GC, outbox voltaram com os dados);
     3. transação: `restore:<id>` (bookmark do estado restaurado, melhor esforço) e `done`, só se ainda `applied` (duas conclusões concorrentes gravam uma linha só).
     O boot já migrou para o schema atual se o bookmark é anterior a uma migração (o cache de schema por isolate é limpo antes do abort). Limite conhecido: os resultados vivem no shard, então um restore posterior para antes deste `nonce` os desfaz; se a entrada deste `nonce` ainda estiver no diário (baixa falhou), o alarm refaz a conclusão no estado atual (epoch novo, linhas `undo:`/`restore:` repetidas), sem mudar dados nem a resposta já dada.
  4. O Worker (`POST /api/_ember/restore`) só responde `ok` depois de um `restoreFinish` bem-sucedido, e então dá baixa no diário. Se a requisição morre entre 1 e 3, o **alarm do System DO** completa a entrada (10 s depois do prepare, backoff até 10 min): `restoreFinish`; `restore_not_applied` → aborta de novo; `restore_not_scheduled` → descarta. Sem binding `SYSTEM`, não há diário (só o Worker conclui).
  - Crash entre passos: antes de agendar → nada mudou. Entre agendar e o abort → aplica no próximo restart e o System conclui. Entre o restart e o finish → o shard atende o estado restaurado com o epoch antigo por esse intervalo; o finish troca o epoch e derruba os sockets desse intervalo. Escritas aceitas entre prepare e o restart são desfeitas como tudo depois do alvo (ficam no undo).
- **CLI** resolve `--to`: bookmark cru; `deploy:<versão ou prefixo ≥4>` (ver abaixo; prefixo ambíguo recusado); hora ISO, epoch ms ou relativa (`-2h`) → o bookmark gravado mais novo `<=` à hora (linhas sem bookmark ignoradas; depois de um restore, linhas reimportadas apontam para o timeline desfeito: "o estado como era naquela hora"). Recusa alvo fora de 30 dias − 10 min.
- **`--to deploy:X`** (`--shard` e `--all` com a mesma regra): por shard, o estado **imediatamente antes de rodar X ou qualquer versão publicada depois de X**: tudo o que X e o código posterior escreveram volta, nada anterior a X volta. Alvo = a linha de boot (`deploy:*`/`deploy-missed:*`) mais antiga (por `id`) que é de X (por versão, sem depender de relógio) ou foi gravada em/depois de `deployedAt` (o primeiro `deployments.at` de X no registro). Logo: shard criado sob X → `deploy:X` (vazio); shard criado depois, sob Y → `deploy:Y` (vazio: não existia quando X entrou); shard que não rodou X → seu primeiro boot depois de X entrar (nada mudou entre X e esse boot: entre deploys um shard só escreve depois de bootar, e todo boot sob versão nova grava a linha); X publicado de novo num rollback → vale a primeira vez. Sem linha de boot e sem atividade depois de `deployedAt` → já está nesse estado (pula). **Recusa** (o shard bloqueia o `--all` inteiro; restaure-o por hora): o alvo é `deploy-missed`, ou há outra linha (`hourly`, `manual`, …) gravada depois de `deployedAt` antes do alvo ou sem alvo (o shard rodou sem registrar o boot). Não é "o bookmark mais novo `<=` deployedAt": esse pode ser horas ou dias mais velho e desfaria escritas legítimas do código anterior. `deployedAt` desconhecido (sem registro) → só shards com linha própria de X resolvem. Algum shard sem alvo válido → nada é feito. Os undos ficam em `.ember/restores/<label>.json`.
- **Limites:** só os dados do shard voltam. Objetos do R2 já apagados pelo GC (refcount 0 há 24 h) não voltam (as linhas `_files` sim); índices externos (Vectorize/AI Search) não são reconstruídos (um documento ressuscitado só volta ao índice quando for escrito de novo); o catálogo D1 e o change log de outros shards não mudam. Escritas de instâncias da versão anterior nos segundos depois do deploy não entram no ponto `deploy:X`.

## Rotação de chaves (`ember keys rotate`)
- **Gerações de secret** (secrets de Worker não podem ser lidos de volta): `<NOME>` é a geração 0 e `<NOME>_R<n>` a geração n. O runtime **assina com a maior** e **verifica com todas** as que estão ligadas (`rotatedSecrets(env, nome)`). Rotacionar = subir `_R<n+1>` (`PUT .../secrets`) e apagar as gerações `< n` (a anterior continua verificando até a próxima rotação). O deploy considera qualquer geração ao decidir se gera o secret.
- `--files`: `EMBER_STORAGE_SECRET[_R<n>]` (URLs de download do modo proxy, vida ≤ TTL + 5 min). Sem downtime.
- `--jwt` (padrão): `POST /api/_ember/keys/rotate` (admin) → `EmberAuthHook.rotateKeys(env)` → RPC `Auth.rotateJwks()`: toda chave viva ganha `expiresAt = agora` (o Better Auth para de assinar com ela e continua publicando em `/api/auth/jwks` pelo `jwks.gracePeriod`, 30 dias) e um JWT assinado em seguida cunha a chave nova; o verificador do Worker descarta o cache. A CLI então regrava `EMBER_AUTH_JWKS` com o JWKS público (status HTTP do `GET /api/auth/jwks` checado antes; falha → erro com o status, a chave nova já está valendo). Tokens já emitidos (TTL 5 min) continuam válidos. Sem logout. Projeto sem DO `Auth` (SSO, sem auth) → 404.
- `--auth-secret --yes`: `EMBER_AUTH_SECRET_R<n>`; o Auth DO passa ao Better Auth `secrets` versionados (o mais novo assina e cifra) com a geração 0 como `secret` legado (decifra material cifrado antes da primeira rotação; nunca é apagada pela rotação). Depois roda `--jwt` (chave nova cifrada com o secret novo). **Encerra as sessões por cookie** (assinadas com o secret antigo).

## Arquivos (`@freecorps/ember-server` ⇄ `@freecorps/ember-runtime` ⇄ `@freecorps/ember-client`)
- **Tabela `_files` por shard** (DDL `FILES_DDL`, criada pelo engine em `migrate()` e pelo runtime no boot):
  `id` (`_storage_<ULID>`), `sha256`, `size`, `content_type`, `refcount`, `state` (`pending|ready|deleting|failed`), `key`, `etag`, `token`, `multipart`, `created_at`, `updated_at`, `zero_since`.
- **Chaves:** `f/<b64url(shard)>/<sha256>` (definitiva) e `t/<b64url(shard)>/<storageId>` (temporária). `parseFileKey` recupera o shard da chave.
- **Dedup por shard:** cada shard é dono do seu prefixo. Não existe registro global de refcount.
- **Engine:** `createEngine({..., storage: { shard: () => string | null, signer?: FileSigner, gcGraceMs?, urlTtlSeconds? }})`.
  - `QueryCtx.storage`: `getUrl(id, {expiresIn?, download?})`, que devolve `string | null` (só para arquivo `ready`), e `getMetadata(id)`.
  - `MutationCtx.storage`: o mesmo, mais `generateUploadUrl(opts)`, que devolve um `UploadTicket`, e `delete(id)`, que lança `FileInUse` se `refcount > 0` e, senão, deixa o arquivo pronto para o próximo GC.
  - Refcount: insert, patch, replace e delete de tabela com `v.file()` (inclusive aninhado em objeto, array, record ou union) aplicam deltas em `_files` na mesma transação. Uma referência nova exige linha `pending` ou `ready` (senão `FileNotFound`). Dentro de union, só contam strings no formato de storage id.
  - `getUrl` assina com `now` arredondado para janelas de 5 min e `expiresIn = ttl + 300` s. O valor fica igual dentro da janela, o que deixa o resultado da query estável.
- **`UploadTicket`**: `{storageId, shard, token, exists?, url?, method?: "PUT", headers?, multipart?: {partSize}, expiresAt}`. O `token` é a capacidade usada nos endpoints `/api/storage/*`.
- **`FileSigner`** (síncrono):
  - `s3Signer(S3Config)`: presign SigV4 em `https://<acct>.r2.cloudflarestorage.com/<bucket>/<key>`. Assina `content-type`, `content-length` e `x-amz-checksum-sha256` quando são conhecidos.
  - `proxySigner({secret, baseUrl?})`: devolve `/api/storage/put|part?shard&id&token` e `/api/storage/get?k&exp&ct?&dl?&sig`, com `sig` = HMAC-SHA256(secret, `"ember-get\n" + k + "\n" + exp + "\n" + ct + "\n" + dl`).
  - O runtime escolhe pelo env (`fileSignerFromEnv`). Usa S3 se houver `EMBER_R2_ACCESS_KEY_ID`, `EMBER_R2_SECRET_ACCESS_KEY`, `EMBER_R2_ACCOUNT_ID` e `EMBER_R2_BUCKET` e `EMBER_FILES_MODE !== "proxy"`; senão, proxy, com `EMBER_STORAGE_SECRET` (sem ele, um segredo de dev com aviso) e `EMBER_PUBLIC_URL`.
  - Sem o binding `EMBER_FILES` não há signer, e quem precisa dele lança `StorageError`.
- **Endpoints do Worker** (CORS `*`, expõem `ETag`):
  - `PUT /api/storage/put`: proxy; o binding confere o `sha256` nas chaves `f/`.
  - `PUT /api/storage/part?uploadId&part`: proxy.
  - `POST /api/storage/multipart {shard, storageId, token, op: create|parts|complete|abort, uploadId?, partNumbers?, parts?}`. `create` devolve `{uploadId, partSize, parts}`. `complete` já confirma.
  - `POST /api/storage/confirm {shard, storageId, token}` → `{ok, file: FileMetadata}`. Se o objeto ainda não existe → 409 `not_uploaded`. Tamanho ou checksum errado → 400, e o objeto é apagado.
  - `GET /api/storage/get`: proxy; aceita `Range`.
- **Confirmação** (`confirmUpload`, idempotente):
  - Chave `f/`: confere o checksum sha256 guardado no R2 ou recalcula o hash.
  - Chave `t/`: calcula o hash com `DigestStream`, copia para `f/<sha>` se ainda não existir, marca `ready` e apaga o `t/`.
  - Enquanto uma linha `deleting` usa a chave de destino, `markReady` e `register` recusam com `StorageError` (tente de novo).
- **RPC do Shard** (`FileRpc`, resultados `{ok, value} | {ok:false, code, message}`): `fileUploadTarget`, `fileReady`, `fileFail`, `filesByKey`, `fileMeta`, `fileUrl`, `fileRegister`, `fileGenerateUpload`, `fileDelete`.
- **Queue:**
  - O `queue()` do Worker reconhece mensagens de evento do R2 (`{account, bucket, action, object:{key}}`) pelo formato.
  - Eventos de create confirmam as linhas `pending` com aquela chave. Eventos de delete, de lifecycle e chaves alheias recebem `ack`. Erro 5xx vira `retry()`.
- **GC** (alarm do shard; o `armAlarm` considera `nextGcAt`):
  - `gcBegin` marca como `deleting` até 100 linhas com `refcount = 0` e `zero_since <= now - grace` (para upload `pending` ainda não apagado explicitamente, `zero_since <= now - max(grace, TTL da URL + 5 min)`, para não coletar um upload em andamento), mais linhas `deleting` paradas há mais de 60 s.
  - Os objetos que nenhuma linha viva compartilha são apagados com `bucket.delete(keys)`. Depois `gcFinish` apaga as linhas.
  - Falha no R2: tenta de novo em 60 s.
  - Grace: `config.files.gcGraceMs`, senão a var `EMBER_FILES_GC_GRACE_MS`, senão 24 h.
- **Actions:**
  - `ctx.storage`: `getUrl`, `getMetadata`, `get` (stream), `store(bytes | Blob | string, {contentType})` (calcula o hash, faz `put` se a chave não existe, registra; dedup), `generateUploadUrl` e `delete`.

## `ember dev --remote` (bindings remotos no dev) — PLAN §11
- Opt-in: `ember dev --remote [--env dev]`. O Worker continua local (Miniflare/workerd: shards, auth, scheduler, arquivos no R2 local), mas estes bindings vão para recursos reais de **um ambiente**: `EMBER_AI` (Workers AI), `EMBER_VEC__*` (os índices Vectorize do env), `EMBER_BROWSER` (`resources.browser`) e `EMBER_IMAGES` (`resources.images`). Sem fila de indexação: o shard local entrega no próprio turno direto ao índice remoto. **AI Search fica no fallback local** (BM25 no SQLite do shard): o proxy remoto do wrangler não transporta o binding de instância (medido em 2026-11-05, wrangler 4.157: `items.upload` → "The RPC receiver does not implement the method upload", `search()` → "internal error"; o AI Search também não está na lista de bindings remotos da Cloudflare); o `ember dev` avisa.
- Mecanismo: `startRemoteProxySession` do wrangler (o mesmo do `remote: true` no wrangler.jsonc), com `auth` = o token de sempre da CLI (`CLOUDFLARE_API_TOKEN` ou o OAuth do wrangler, nunca impresso) e `workerName` `ember-<project>-<env>-dev-proxy`; a `remoteProxyConnectionString` vai em cada binding das opções do Miniflare (`ai`, `vectorize`, `browserRendering`, `images`). `wrangler` é peer opcional da CLI, carregado do projeto. Só roda em Node (o wrangler recusa Bun).
- Env: `--env`, senão `dev` se existir no `ember.json`; nunca `prod` implicitamente. Os índices Vectorize do env que faltam são criados (os mesmos nomes do `ember deploy`, sem a fila). Mudou o schema de índices externos durante o dev → aviso para reiniciar.
- **Trade-offs:** (1) custo: cada embed, busca, PDF e transform é cobrado como em produção; (2) latência: cada chamada atravessa a rede até a Cloudflare (medido em `docs/spikes/remote/integrations-e2e.md`); (3) dados compartilhados: escritas do dev caem nos índices reais do env — o shard isola (namespace/`_shard` no Vectorize, pasta no AI Search), mas shards com o mesmo nome no dev e no deploy do mesmo env se misturam; use um env `dev` dedicado; (4) sem `--remote` nada sai da máquina: fallback local explícito para índices (`EMBER_AI_INDEXES=local`) e `ctx.browser` → `BrowserNotConfigured`.

## Telemetria, registro e painel (Fase 4b)
- **Métricas** (`@freecorps/ember-runtime` `metrics.ts`): binding Analytics Engine `EMBER_METRICS` (um dataset por conta, padrão `ember_metrics`; `ember.json` `metrics: { enabled?, dataset?, sample? }`). Sem binding: no-op. Nunca lança.
  - Um ponto por execução: `index1 = "<project>/<env>"`; `blob1..9 = project, env, shardKind, fn, kind, status, errorCode, shard, timing`; `double1..5 = durationMs, rowsRead, rowsWritten, bytesOut, weight`.
  - `kind`: `query` (RPC/HTTP), `subscription` (reexecução reativa), `mutation`, `job` (mutation agendada/cron), `action` (no Worker; linhas contadas pelas chamadas ao shard).
  - Group commit: linhas do lote divididas igualmente entre os itens; a duração (`commit`) é de cada item, do seu recebimento à durabilidade do lote. Linhas = contadores do `DoSqlDriver` em volta da chamada ao engine.
  - `EMBER_METRICS_SAMPLE` (0..1) amostra os ok; erros sempre; `weight = 1/rate`. Contagem = `SUM(_sample_interval * double5)` (o próprio Analytics Engine também amostra).
  - `blob9 = timing` diz **o que `durationMs` mede** (Fase 5b). Em produção o relógio do Workers só anda com I/O, então trabalho SQLite síncrono dentro do DO mede 0; toda duração é tempo de parede tomado onde o relógio anda:
    - `rpc`: no Worker (HTTP `/api/query|mutation`, ou `runQuery`/`runMutation` de uma action), em volta do RPC ao shard: hop até o DO + fila de entrada/group commit + execução + (mutations) o commit durável que a resposta do RPC espera. O caller passa `{ caller: true }` ao `Shard.query/mutation`; o shard não grava ponto e devolve `outcome.metrics = { rowsRead, rowsWritten, bytesOut }` (retirado da resposta HTTP). Chamadas recusadas antes de executar não geram ponto.
    - `commit`: no DO, do recebimento (`mut` por WebSocket; início do job) até a escrita durável (`ctx.storage.sync()`): espera do group commit + execução + durabilidade. O ponto é gravado depois do `sync()` (`waitUntil`).
    - `wall`: actions no Worker.
    - `none`: reexecução de subscription (síncrona no DO): 0 em produção; no workerd local (`ember dev`, testes) os timers andam, então o valor local é real.
    - `""`: pontos anteriores à Fase 5b (0 para query/mutation em produção).
    - Tempo de CPU por chamada não existe na plataforma (só por invocação, em Workers Logs / Tail). O painel e `ember metrics` agrupam p50/p95 por `timing`.
  - `EMBER_TRACE=1` (var) também loga `ember:exec {json}` por execução (filtro do `ember logs`).
- **Catálogo de shards**: binding D1 `EMBER_REGISTRY` (o registro). Cada shard faz upsert em `shards(project, env, shard, kind, key, schema_version, db_size, last_write, reported_at)` depois de migrar (quando já sabe o nome) e na manutenção horária (no máximo 1×/50 min). Escolha: binding D1 direto em vez de Queue — um upsert por shard por hora, sem consumer nem fila extra. Falha = log, nova tentativa no próximo report.
- **Admin** (mesmo `EMBER_ADMIN_TOKEN` do status): `GET /api/_ember/data?shard=&table=&cursor=&limit=` (sem `table`: lista tabelas do schema + `_jobs`, `_files`, `_ember_migrations`, `_ember_bookmarks` com contagem; com `table`: página por `_rowid`/`rowid`, até 200, documentos decodificados, colunas `_k_*` omitidas, `{rows, cursor, done}`; 404 tabela desconhecida). `GET /api/_ember/crons` → crons resolvidos + estado do System.

- **Domínios**: `ember domains add <host>` acha a zona (sufixo mais longo), recusa se o host é Custom Domain de outro Worker, casa com rota de outro Worker, ou está no registro para outro projeto/env; senão `PUT /workers/domains` e grava no registro.

## Índices externos: Vectorize e AI Search (`@freecorps/ember-server` ⇄ `@freecorps/ember-runtime` ⇄ `@freecorps/ember-cli`) — Fase 5b
Kinds de índice embutidos (como `searchIndex`), com `external` no `IndexKind`: `ddl` vazio, `backfill = externalBackfill`, sem `query` (não são lidos em query/mutation, não são reativos). Consulta só em actions.
```ts
defineTable({ title: v.string(), body: v.string(), lang: v.string(), vec: v.array(v.number()) })
  .vectorIndex("by_vec", { vectorField: "vec", dimensions: 768, metric?: "cosine" | "euclidean" | "dot-product", filterFields?: ["lang"] })
  .vectorIndex("semantic", { embed: "body" /* ou { field, model } */, filterFields?: [...], shardIsolation?: "namespace" | "filter" })   // dimensions vem do modelo
  .aiSearchIndex("hybrid", { fields: ["title", "body"], filterFields?: ["lang"], embeddingModel?: "@cf/baai/bge-m3",
                            defaultMode?: "hybrid" | "vector" | "keyword", keywordTokenizer?: "porter" | "trigram" })

ctx.vectorSearch("notes", "by_vec", { vector, limit?: 10 /* ≤100 */, filter?: { lang: "pt" | { $eq,$ne,$in,$nin,$lt,$lte,$gt,$gte } }, shard? })
  → Promise<{ _id: Id<"notes">; _score: number }[]>          // { text } no lugar de { vector } com embed
ctx.aiSearch("notes", "hybrid", { query, limit?: 10 /* ≤50 */, filter?, mode?: "hybrid" | "vector" | "keyword", fusion?: "rrf" | "max", shard? })
  → Promise<{ _id: Id<"notes">; _score: number; text: string }[]>   // um item por documento (melhor chunk)
```
- **Validação no `defineSchema`:** `vectorField` é `v.array(v.number())`; exatamente um de `vectorField`/`embed`; `dimensions` 32..1536 (faixa do Vectorize, medida); modelo de embed conhecido define `dimensions` (bge-m3 1024, qwen3 1024, embeddinggemma 768, bge-*-en). Filtros: string/number/boolean/id (inclusive aninhados), até 10 (Vectorize, chave = caminho com `.`→`_`) ou 5 (AI Search, chave em minúsculas, sem `timestamp`/`folder`/`filename`).
- **Outbox** (`_ember_ext_outbox(tbl, idx, doc_id, seq, sent, sent_at, attempts)`, criada pelo `SYSTEM_DDL`): o engine grava uma linha **na transação da mutation** quando uma escrita muda um campo do índice (insert, delete, ou patch/replace que toca `spec.fields`); linhas coalescem por documento; `seq` é um token aleatório novo por escrita. Linhas na janela de um backfill staged ficam para o backfill. Réplicas locais (offline) nunca preenchem o outbox.
- **Backfill/reindex:** índice novo, ou spec alterada (filtros, dimensões, métrica, modelo), numa tabela com dados vira *staged*; `backfillStep` insere uma linha de outbox por documento (o mesmo mecanismo de `.index()`), e a entrega reenvia tudo.
- **Entrega** (`outboxClaim`/`outboxFetch`/`outboxAck`, puras sobre `SqlDriver`):
  - Depois de cada commit com mudanças (e no alarm), o shard reivindica linhas `sent = 0` (ou em voo há mais de `resendMs`), marca `sent = claim` (um **token de claim** aleatório novo por reivindicação) e manda **uma mensagem por ≤50 documentos de um índice** para a Queue `EMBER_INDEXING`: `IndexMessage = { t: "ember.index", shard, table, index, ids, claim }`. Sem Queue (dev, testes), o próprio shard indexa no seu turno.
  - O consumer (`queue()` do Worker, ou o shard) chama `Shard.extFetch(…, claim)` → estado **atual** + `seq` lido + `current` (o claim da mensagem ainda é o da linha), escreve no serviço só os itens `current` e chama `extAck(acks, claim)`.
  - **Reenvio e cercas (fencing):** uma linha sem ack é reenviada após `resendMs` com um claim novo, então duas entregas do mesmo documento podem se sobrepor (a primeira só lenta). A escrita no serviço não pode ser condicional; quem cerca é o ack:
    - claim atual e mesmo `seq` → linha apagada (pronto);
    - claim atual e `seq` mudou (escrita no meio) → volta a `sent = 0` e é reenviada com o estado novo;
    - claim superado → a escrita desta entrega pode ter caído **depois** da mais nova: a linha ganha um `seq` novo, sem zerar `attempts` (linha estacionada continua estacionada até o documento mudar), e a entrega mais nova em voo falha a própria checagem de `seq` e reenvia;
    - linha sumida (outra entrega já confirmou) → reenfileirada como uma escrita do documento, então uma entrega reivindicada depois deste ack regrava o estado mais novo.
    - Entrega cujo claim já está superado no `extFetch` (duplicata da Queue, reenvio) pula o documento: sem escrita, sem ack. Mensagem sem `claim` (versão anterior) conta como superada. Exceção: numa **reentrega** da Queue (`attempts > 1`), a tentativa anterior pode ter escrito antes de falhar; os itens superados são então confirmados com o claim antigo, o que cai no caminho "claim superado" e garante mais uma entrega do estado mais novo.
  - **Invariante:** a última escrita no serviço para um documento é sempre seguida de uma entrega do seu estado mais novo; o índice externo converge para o estado atual do documento (estados velhos podem aparecer por um instante, nunca ficam por último). Prova curta: uma linha só sai com um ack de claim atual e `seq` igual ao lido; qualquer outra entrega que tenha escrito depois dessa escrita confirma depois dela e encontra a linha sumida/com outro claim → reenfileira.
  - Falha: `msg.retry({ delaySeconds: 5·2^n, ≤300 })`; sem ack, reenvio após 10 min (fila) ou 15 s (em processo); `sendBatch` que falha adia 30 s. Depois de 10 envios sem ack a linha é estacionada (`sent = -1`, log) até o documento mudar de novo. Linhas de índice que saiu do schema são descartadas.
  - `inspect().outbox = { pending, inFlight, parked }`.
- **Vectorize:** um índice por `(project, env, tabela, índice, dimensões, métrica, modelo)`; binding `EMBER_VEC__<tabela>__<índice>`; vector id = `_id` do documento (≤64 bytes); **namespace = shard** (`vectorNamespace`: o nome do shard, ou `h:<sha256[0..40]>` acima de 64 bytes); metadados = filtros; `query(vector, { topK, namespace, filter, returnMetadata: "none" })`.
  - **Mais shards que namespaces** (`shardIsolation: "filter"`; o padrão é `"namespace"`): o Vectorize aceita 50.000 namespaces por índice. Em modo `filter` o vetor vai **sem namespace**, com o shard (o mesmo valor de `vectorNamespace`) na propriedade de metadado `_shard` (metadata index `string`, criado antes dos outros e antes do upload), e toda busca leva `filter: { ...filtroDoUsuário, _shard: { $eq: ns } }`. Ocupa um dos 10 slots (sobram 9 `filterFields`; `_shard` é reservado). A spec só ganha `shardIsolation: "filter"` nesse modo (índices existentes não mudam de spec nem de nome); a identidade do índice ganha `/shard-filter`, então **trocar de modo = índice novo + staged backfill** e o antigo é apagado no prune depois do deploy a 100% (até o backfill terminar, a busca vê o índice novo incompleto, como numa troca de dimensões). O `ember deploy` conta os shards de cada tipo no catálogo (D1) e avisa a partir de 80% (40.000) para índices em modo namespace. Não há troca automática: o Vectorize não informa quantos namespaces um índice tem, e a troca exige reindexar tudo.
  - Embed: `EMBER_AI.run(model, …)` no consumer (documentos) e na busca (consulta), com a forma de entrada de cada modelo.
- **AI Search** (verificado na doc e numa sonda real em 2026-11-04): instância por `(project, env, tabela, índice)` no namespace `default` (binding de instância `ai_search`, `EMBER_AIS__<tabela>__<índice>`; nenhum dos 100 namespaces da conta é usado). Item = `s<sha256(shard)[0..32]>/<_id>.md` (`aiSearchItemKey`), texto = os `fields` em seções markdown, `metadata` = filtros como strings: o upload só aceita `Record<string, string>` (Items API), e o AI Search converte cada valor para o `data_type` do `custom_metadata` da instância ao indexar (`number` vira float, `boolean` aceita true/false/1/0/yes/no); os filtros de busca vão tipados (`{ stars: { $gte: 3 } }`, como na doc). Declarar tudo `text` e passar filtros como string deixaria faixas numéricas lexicográficas. Reenviar a mesma chave substitui o item (mesmo id, medido); delete procura o id por chave (`items.list({ search })`). A pasta (`folder`, filtro embutido) isola o shard, então os 5 campos custom ficam para `filterFields`. Busca com `cache: { enabled: false }` (o cache de similaridade, ligado por padrão por 48 h, devolveu resultado velho na sonda), `keyword_match_mode: "or"` (`and` não achou perguntas naturais em pt-BR), `max_num_results = 2·limit`, `filters: { folder, ...filtro }`; os chunks são agrupados por documento.
  - **Modo padrão e tokenizer:** `defaultMode` vale para buscas sem `mode` (padrão `hybrid`). `keywordTokenizer` vai em `indexing_options.keyword_tokenizer` da instância (`porter`, o padrão do AI Search: palavras com stemming inglês; `trigram`: trigramas de caracteres, sem stemming, qualquer idioma). Não existe opção de idioma nem de stemmer (API conferida em 2026-11). Medido em pt-BR (`docs/spikes/remote/integrations-e2e.md` §5): MRR@10 híbrido porter 0,681, híbrido trigram 0,717, vetor 0,950 nos dois. **Para pt-BR: `defaultMode: "vector"`**; trigram se o híbrido for necessário. Os dois ficam na spec só quando definidos e **fora da identidade do índice** (`IndexKind.identity`): mudar `defaultMode` não reindexa nada; mudar o tokenizer é um `PUT` na instância e o próprio AI Search reindexa (sem backfill do Ember).
  - **Preço:** a cobrança do AI Search começa em **2026-12-01**: por mês 5 M tokens de ingestão, 10 GB-mês, 1.000 consultas semânticas e 1.000 full-text inclusos; depois $0,75/M tokens de ingestão, $2,00/GB-mês, **$0,75 por 1.000 consultas semânticas/vetor/híbridas**, $0,10 por 1.000 full-text. Embedding e reranking do Workers AI dentro do AI Search entram nesse preço. Até 5.000 instâncias no plano pago (depois $0,10/instância/mês), 1 M arquivos por instância (500 k com híbrido).
- **Fallback local explícito:** `EMBER_AI_INDEXES = "local"` (o `ember dev` define) e binding ausente → o shard guarda o índice no próprio SQLite (`_ember_ext_local`) e busca por força bruta: vizinhos exatos com as mesmas métricas e semântica de filtro do Vectorize; texto por BM25 (sem vetor, sem chunks); embeddings de `EMBER_AI` se houver, senão `hashEmbedding` (só palavras em comum, não semântico). Sem a flag, binding ausente = `IndexNotConfigured`, nunca fallback silencioso.
- `config.externalIndexes.env(env)` sobrepõe os bindings que o indexer e as buscas usam (fakes nos testes; proxies remotos).
- **Deploy** (`deploy/ai.ts`), antes do upload: índices Vectorize (`POST /vectorize/v2/indexes`, descrição `ember:<project>/<env> <tabela>.<índice> (<dims>/<métrica>/<modelo>)`) + um metadata index por filtro (a lista devolve `"String"`, o create recebe `"string"`; propriedades que saíram de `filterFields` são apagadas com `POST …/metadata_index/delete { propertyName }` no prune, ou já antes do create se as novas não cabem nos 10 slots do Vectorize); instâncias AI Search (`POST /ai-search/namespaces/default/instances` com `embedding_model`, `cache: false`, `custom_metadata`, `retrieval_options.keyword_match_mode: "or"`; `PUT` quando muda); Queue `ember-<project>-<env>-indexing`. Depois do upload: consumer da Queue. Bindings (`vectorize`, `ai_search`, `ai`, `queue`) vão em todo deploy, então um deploy só de código os mantém. Depois do deploy a 100%: **prune** dos recursos deste env que o schema não usa mais (dono pela descrição no Vectorize e pelo prefixo `ember-<project>-<env>__` no AI Search; nunca por prefixo de nome solto); deploy gradual não faz prune; quando a fila de indexação sai, a Worker é tirada dos consumers dela antes do delete (o mesmo `detachQueueConsumer` do `ember destroy`). Nomes: Vectorize `ember-<project>-<env>-<tabela>-<índice>-<hash8>` (o hash cobre dimensões/métrica/modelo: mudar = índice novo + backfill, o velho é apagado depois), AI Search `ember-<project>-<env>__<tabela>_<índice>_<hash6>`.
- **`ember destroy --env X --yes`:** tira a Worker dos consumers das filas do env (a Cloudflare recusa apagar um consumer), apaga a Worker (com os dados dos DOs), os recursos de índice externo do env, a fila de indexação, a fila de arquivos e o bucket (se vazio).
- **Trace:** com `EMBER_TRACE=1`, o consumer loga `ember:index {shard, index, upserted, deleted, attempt, queuedMs, deliverMs}` por mensagem.
- **Codegen:** `action`/`internalAction`/`httpAction` e `ActionCtx` gerados recebem o `DataModel`; buscas checadas por tabela, índice, `{ text }` só com `embed`, campos e tipos de filtro. Sem codegen (`ActionCtx` genérico), qualquer nome é aceito.

## Offline (`@freecorps/ember-client` ⇄ `@freecorps/ember-offline` ⇄ `@freecorps/ember-server`) — Fases 5a e 5c
Opcional (D1). Sem `StorageAdapter`, o cliente é o de sempre (cache em memória + `PendingStorage`).

**Contrato no cliente** (`@freecorps/ember-client`, `storage.ts`): `EmberClientOptions.storage` aceita `PendingStorage` (como antes) ou um `StorageAdapter` (reconhecido por `applyPatch` + `runQueryLocally`).
```ts
interface StorageAdapter {
  load(): Promise<{ identity?: LocalIdentity | null } | void>      // 1ª coisa do init: abre/migra; identidade da última sessão
  readonly persistPending: PendingStorage                          // clientId + fila de mutations (substitui `storage`)
  applyPatch(u: QueryUpdate): Promise<void> | void                 // cada valor confirmado (snap sem `unchanged`, patch), na ordem do servidor
  runQueryLocally(r: LocalQueryRequest): Promise<LocalQueryResult | undefined> | ...
  watchQueryLocally?(r, onResult: (r: LocalQueryResult | undefined) => void, onError?): () => void   // preferido (5c)
  setIdentity?(id: LocalIdentity | null): ...                       // `sub`/`iss` do JWT atual; null no sign-out
  readonly sync?: readonly SyncSpec[]                              // queries inscritas pela vida inteira do cliente
  flush?(): Promise<void>; close?(): ...
}
type QueryUpdate = { shard; fn; args; argsJson /* stableStringify */; value; version; epoch? /* ready.epoch */ }
type LocalQueryRequest = { shard; fn; args; argsJson; identity: LocalIdentity | null }
type LocalQueryResult = { value: unknown; source: "local" | "cache" }
type SyncSpec = { query: string | FunctionReference<"query">; args?; shard? }
type LocalIdentity = { subject: string; issuer?: string }
```
- Uma inscrição nova pede `watchQueryLocally` (ou, sem ele, `runQueryLocally` uma vez) depois do `load`. Enquanto o servidor não responde, o snapshot é `success` com o valor local e `source: "local" | "cache"`, e é **reexecutado** sempre que a réplica muda dentro do que ele leu (um `undefined` do watch — registro apagado por `clear()`, eviction — volta a inscrição para `loading`); o primeiro `snap`/`patch` substitui (sem `source`) e encerra o watch: o servidor continua ganhando. Updates otimistas são aplicados sobre `confirmed ?? local` (a cada novo valor local também), então funcionam offline desde o cold start.
- `options.optimisticUpdates: { "<fn>": update }`: update por nome, usado quando a chamada não passa um e nas mutations restauradas do armazenamento (os closures se perdem no restart). Assim a edição offline continua visível depois de recarregar; a reconciliação é a de sempre (`patch.mids` derruba a camada, `mres` resolve, rejeição desfaz).
- Mutations restauradas vão primeiro e são reenviadas com o mesmo `mid` no `ready` (dedup por `(identity, clientId, mid)`); o `mres` remove do `persistPending`.
- `load()` que falha: o cliente segue sem offline (memória) e reporta `storage_error`.
- `client.flushStorage()`: espera as escritas entregues ao adapter.

**Execução local** (`@freecorps/ember-server`, `local.ts`, TS puro):
- `QueryImpl` lê por `QueryEnv.scan(t, index, lo, hi, asc, limit)` e `QueryEnv.pluginQuery(kind, t, spec, arg)`. O engine implementa com `sqlScan` / `sqlPluginQuery` (o SQL de antes); réplicas locais implementam com o mesmo encoding de chave. Ranges, filtros, ordem, cursores de paginação (interoperáveis com o servidor) e read sets saem do mesmo código.
- `runLocalQuery(fn, args, { schema, reader: LocalReader, identity?, now?, rowsRead? })`: valida args e retorno como o engine; `ctx.db.get/query/normalizeId` e índices de plugin que o reader suporta. `ctx.db.get` (e `withIndex("by_id")`) entra no read set como leitura pontual `by_id`, como no engine, então um resultado local observado reexecuta quando aquela linha muda. `ctx.db.aggregate`, `ctx.db.sql` e `ctx.storage` lançam `OfflineUnsupported`. Limite de 16k linhas lidas.
- Só `query()` **públicas registradas explicitamente** rodam no cliente (`localQueryRegistry`/`assertLocalQuery`: mutation, action, internal → `InvalidFunction`). O cliente importa as mesmas definições `query()` dos módulos `ember/` (são puras: só leitura síncrona).
- `LocalReader { scan, get, pluginQuery? }` é síncrono. Stores assíncronos (IndexedDB) servem o que já buscaram, registram o resto como *miss* (lançando `NeedData`) e a query é reexecutada depois do `fetch()` (até nada faltar). Na leitura de linhas por id (resolver referências de um valor em cache) são até 100 rodadas: o que ainda faltar conta como linha ausente (`null`) e o valor falha, nunca volta com buracos (`undefined`).
- Schema: `LocalSchema = { manifest, indexKinds }` — o `SchemaDefinition` do app, ou `localSchema(manifestJson.schema, plugins?)` a partir do `_generated/manifest.json` do codegen.
- `documentsIn(manifest, value)`: documentos completos num resultado (arrays, `{page}`, objetos aninhados): `_id` de tabela conhecida, `_creationTime` number, campos válidos pelo shape da tabela. Projeções e objetos calculados ficam de fora.
- SQLite local: `prepareLocalDatabase(driver, schema)` = planner + DDL do servidor (FTS5 `unicode61 remove_diacritics 2` incluído), backfill imediato; migração recusada → `wipeLocalDatabase` + recriação (`{reset: true}`). `sqlReplicaWriter` grava docs com o codec de linha e as chaves do servidor (mantém `_id`/`_creationTime`; triggers FTS acompanham; agregados e `_files` não são mantidos). `sqlLocalReader` lê com o SQL do servidor.
- `localReadSetMatches(schema, readSet, changes: LocalRowChange[])`: o casamento do engine (ranges de índice + `.filter()` + `matchesChange` dos plugins) para mudanças de linhas da réplica; `before: undefined` (versão anterior desconhecida) casa com toda entrada da tabela. Sem falso negativo.
- `jsSearch(docs, spec, build)`: `withSearchIndex` sem FTS5 (mesmo tokenizer, OR dos termos com o último como prefixo, trigram, filtros `.eq`, até 1024), ranking BM25 (k1 1,2, b 0,75) sobre `docs`.

**Store genérico** (`@freecorps/ember-offline`, `createOfflineStorage(backend, { schema, queries?, sync?, maxQueries? = 500, retentionMs? = 30 d })`):
- Registro por `(shard, fn, argsJson)`: último valor confirmado, `version`, `epoch`, `updatedAt`, `ids` (docs completos do valor).
- **Nunca volta para um valor mais velho:** `applyPatch` com `version` menor que a do registro guardado **no mesmo `epoch`** do shard é descartado (duas abas online gravam o mesmo resultado; uma chamada reenviada depois da troca de líder). Versões são por shard e só comparáveis dentro de um epoch (persistido no registro e em cada entrada do log, então vale depois de recarregar): versão igual é aceita (reavaliação depois de sign-out sem commit no meio), epoch novo (restore/PITR reusa versões) ou desconhecido (registro antigo, adapter alimentado sem `epoch`) é aceito como vier.
- **Replicação por posse:** só valores de queries *offline* (registradas em `queries` ou listadas em `sync`) replicam linhas. Uma linha existe enquanto algum registro a possui; quando o novo valor do último dono não a contém mais (apagada no servidor ou fora dos ranges em cache), ela é apagada. A réplica é sempre a união dos últimos resultados do servidor — nunca uma linha que o servidor não mandou. Docs iguais aos do valor anterior não são regravados.
- Queries não registradas só têm o valor em cache (`source: "cache"`).
- `runQueryLocally`: registrada → roda local (`source: "local"`; erro → cache, se houver); senão → cache; senão `undefined`.
- Escritas (resultados, fila, meta) passam por uma fila única (ordem garantida; `flush()`); registro, log e linhas do mesmo shard são gravados atomicamente. Um commit que falha não muda a memória (refcounts, registros, meta): ela só anda depois do backend.
- **Valor por referência + log de rowdiffs (5c):** num registro de query offline, cada documento replicado vira uma referência `{ _id, $row: 1 }` (a linha guarda o conteúdo; `refs: true`, `size` = bytes da base). Um valor novo cujo esqueleto é um array de docs vira um `RowDiff` (o mesmo do protocolo) contra o esqueleto anterior, anexado como `QueryLogEntry { key, seq, diff, version, updatedAt, add, remove }`, mais só as linhas que mudaram. O registro é regravado inteiro (compactação, apaga o log) quando o log passaria do tamanho da base ou de 64 entradas, ou quando não há diff (valor que não é array de docs). Queries só em cache usam o mesmo log, com docs completos no diff. No `open` o log é reaplicado; um log que não aplica descarta o registro. A leitura do valor resolve as referências pelas linhas (cada doc aparece na versão mais nova replicada). `persistDiffs: false` volta ao formato anterior (valor inteiro). Medido (SQLite, resultado de 500 linhas, 100 mudanças de 1 linha): replicada 17 106 KiB → 100 KiB gravados (170×), só cache 15 185 KiB → 201 KiB (75×); tempo igual (193 → 170 ms e 69 → 100 ms: o diff custa CPU, a escrita some). `test/persist-size.test.ts`.
- **Resultados locais reativos (5c):** `watchQueryLocally(req, onResult, onError?)` roda a query (ou lê o cache) dentro da fila de escrita e guarda o read set de `runLocalQuery`. Depois de cada commit o store gera `LocalRowChange`s (doc anterior conhecido em memória, senão `undefined`) e reexecuta os watches cujo read set casa (`localReadSetMatches`); um watch de valor em cache reenvia quando o registro dos seus args muda. Resultado igual ao último enviado não é reenviado. Mudanças de fora (`OfflineBackend.onExternalChange`, ex. o app escrevendo no Store do TinyBase) invalidam o que o store sabia das linhas daquele shard e reexecutam tudo que lê as tabelas.
- Retenção: no `load`, registros sem atualização há mais de `retentionMs` saem (com as linhas que só eles possuíam). Acima de `maxQueries`, sai o menos recentemente atualizado. `clear()` esquece resultados e linhas (a fila fica).
- `OfflineBackend { open → {meta, queries, log?}, setMeta, loadPending, putPending, removePending, commit(shard, {put, drop, append, upsert, delete}), reader(shard), onExternalChange?, close }`. `put` de um registro apaga o log dele; `drop` apaga os dois. O log é chaveado por `(key, seq)` em todos os backends: anexar de novo o mesmo `seq` substitui a entrada.

**Backends:**
- `memoryStorage` / `MemoryBackend`: referência, sem persistência (ou compartilhando o objeto `backend`).
- `sqliteStorage({ open: (name) => SqlDriver, name? })` e `expoSqliteStorage({ openDatabaseSync?, name? })` (`expo-sqlite` é peer opcional, carregado com `require` preguiçoso; FTS5 vem habilitado no expo-sqlite). Banco principal `<name>` (`_ember_local_meta`, `_ember_local_pending`, `_ember_local_shards`) e um banco por shard `<name>-<sha256(shard)[0..24]>` com as tabelas do schema + `_ember_local_queries`. `expoSqliteDriver(db)` usa `getAllSync` (SELECT/WITH/PRAGMA/RETURNING) e `runSync`, savepoints para transações aninhadas, WAL.
- `indexedDbStorage({ name?, indexedDB?, IDBKeyRange? })`: stores `meta`, `pending` (autoIncrement + índice único `mid`), `queries`, e `t:<tabela>` com keyPath `["s", "id"]` (shard, `_id`) e um índice `[s, _k_<índice>]` por índice db (inclui `by_creation_time`), onde `_k_<índice>` é a chave codificada do servidor como `ArrayBuffer`. Cada range é `IDBKeyRange.bound([shard, lo], [shard, hi], false, true)` (IndexedDB compara binário byte a byte, como o BLOB no SQLite); `desc` usa cursor `prev`. Busca carrega as linhas da tabela do shard e roda `jsSearch`. Versão de schema diferente → `versionchange` recria os stores `t:*` e limpa `queries` (a fila fica).

- `sqliteWasmStorage({ open: (name) => oo1 DB, name? })` / `wasmSqliteDriver(db)`: o backend SQLite sobre o build oficial `@sqlite.org/sqlite-wasm` (peer opcional; FTS5 incluído; statements preparados em cache, savepoints). Testado em Node pelo mesmo build (FS em memória) com todos os cenários dos outros backends.
- **OPFS (5c)** — `opfsStorage({ worker })` (`/opfs`, na página) + `serveOpfsStorage({ name?, schema, queries, sync, capacity? = 16, multiTab? = true, onRoleChange? })` (`/opfs-worker`, num Worker dedicado do app). O store inteiro (backend SQLite, `runLocalQuery`) roda no Worker sobre o VFS `opfs-sahpool` (diretório `.ember-<name>`, sem COOP/COEP), porque access handles síncronos só existem em Workers e o `SqlDriver` é síncrono; a página fala com ele pelo protocolo de `remote.ts`. `close()` fecha os bancos e pausa o VFS (libera os handles); `openOpfsStore` que falha depois de instalar o VFS também o pausa. Worker que não sobe (evento `error`) → `load()` rejeita → cliente segue sem offline. Um `error` do Worker depois do `load` (crash, abort do wasm, OOM) é definitivo: chamadas em voo e novas falham com ele, cada watch recebe o erro uma vez, um `leader` atrasado não o revive, e o Worker é terminado (solta os handles do OPFS e, com várias abas, o lock de líder para a próxima). `close()` da página não espera um Worker morto: desiste ao ver o `error` do Worker ou depois de `closeTimeoutMs` (padrão 5000), rejeita o que estava em voo e chama `terminate()`. Escolha: `@sqlite.org/sqlite-wasm` em vez de wa-sqlite — o wasm do pacote npm `wa-sqlite` (1.0.0, publicado em 2024; 273 KB gzip) não tem FTS5 (exigiria build próprio) e o fork ativo (`@journeyapps/wa-sqlite`) publica vários builds (17 MB no pacote); o oficial é mantido pelo projeto SQLite, traz FTS5 e o `opfs-sahpool` num wasm de 879 KB (407 KB gzip) e tem build Node, o que permite testar em Node o mesmo binário do navegador.
- **TinyBase (5c)** — `tinybaseStorage({ store, persister?, schema, queries, sync })` (`/tinybase`, `tinybase` ≥ 5 peer opcional): um `OfflineBackend` sobre o `Store` do app (não um persister: persister só copia o Store inteiro e não responde ranges por chave codificada). Uma tabela TinyBase por tabela Ember (row id `_id`, células = campos; bigint/bytes/NaN na forma tagged do JSON do Ember; linhas de shards além do primeiro com célula `_shard`), estado do Ember em `_ember_queries`/`_ember_log`/`_ember_pending` e valores `_ember_*`. Leituras: chaves codificadas ordenadas em memória por (tabela, índice, shard), invalidadas por listener; busca por `jsSearch`. Escritas em `store.transaction`; cada uma guarda o que sobrescreve e, se o `save()` do persister falha, devolve o Store (linhas, registros, log, valores, lista de shards) ao estado anterior, então o Store nunca guarda o que o store genérico ouviu como falha; escritas de outros (o app) são vistas por listener e reexecutam queries locais (o próximo valor do servidor sobrescreve). Persistência: qualquer persister TinyBase no mesmo Store (`persister` → `load()` no open e `save()` após cada escrita, ou auto-load/save do app). Schema novo → limpa as tabelas Ember e os registros (fila e meta ficam).

**Abas (5c)** — `coordinateTabs({ name, open, locks?, channel?, openAttempts? = 10, onRoleChange? })` (`TabCoordinator`, um `StorageAdapter`): várias abas com o mesmo nome de armazenamento; só o líder abre e escreve (réplica, registros, fila). `role`: `starting` → `leader` | `follower` | `failed` → `closed`.
- Eleição por Web Lock `ember-offline:<name>` (`ifAvailable` na partida; senão segue na fila com `signal`); cada aba segura `ember-offline:<name>:tab:<id>` pela vida inteira, e o líder espera esse lock para saber que um seguidor morreu (larga os watches dele).
- Protocolo (`remote.ts`, `RemoteStorage`/`serveStorage`) num `BroadcastChannel` `ember-offline:<name>` (e também página ⇄ Worker no OPFS): `{ember:"offline/1", k:"req", id, from, to, op, a}` → `{k:"res", id, to, ok, v|e}`; `{k:"watch", to, wid, r|e}` para resultados observados; `{k:"leader", from}` quando um líder assume; `{k:"bye", from}` quando um chamador sai. Cada envio de uma chamada leva um `id` novo (também no reenvio): só o servidor para quem ela foi enviada por último a responde; um `res` atrasado para um `id` antigo não acha nada. Ops: `load` (+ `sync` do líder, como nomes), `getClientId`, `setClientId`, `loadPending`, `putPending`, `removePending`, `applyPatch`, `runQueryLocally`, `setIdentity`, `flush`, `clear`, `close`, `watch`/`unwatch`. Valores por structured clone.
- Troca de líder: o próximo da fila do lock abre o armazenamento (até 10 tentativas com backoff, enquanto o anterior solta os handles do OPFS), serve o canal e anuncia `leader`; seguidores reenviam tudo que estava em voo (em ordem) e restabelecem os watches; um seguidor que vira líder roda as próprias chamadas pendentes localmente. Toda op é idempotente (resultados por query, fila por `mid`, meta por chave; um `applyPatch` mais velho é descartado), então reexecutar o que o líder morto já tinha feito é inofensivo. Um líder que sai para de servir (`stop()`) **antes** de fechar o armazenamento e não responde mais nada: o que ele ainda estava rodando (e falharia com o erro do fechamento) é reenviado ao próximo, em vez de falhar no seguidor. Um líder sobre um armazenamento sem `watchQueryLocally` dá aos próprios watches o mesmo resultado único (`runQueryLocally`) que `serveStorage` dá aos seguidores.
- Falha ao abrir: cada tentativa que abriu mas não carregou é fechada antes da próxima (não vaza handles do OPFS). Se nenhuma das `openAttempts` tentativas abre, a aba solta o lock e fica `failed` (`RemoteStorage.setUnavailable`): chamadas em voo e novas falham na hora com o erro (pode não haver outra aba para esperar) e cada watch recebe o erro uma vez, mas continua registrado. O próximo da fila tenta por sua vez; quando um líder anuncia `leader`, a aba `failed` passa a segui-lo como qualquer seguidor (chamadas vão para ele, watches são restabelecidos) e volta para a fila do lock, tentando de novo quando ele sair. Sozinha, ela não fica tentando em loop: o lock fica livre e a próxima aba que abrir o armazenamento lidera. Toda aba que não lidera nem falhou está na fila, então uma chamada em voo sempre termina respondida ou com erro, nunca presa. Um `EmberClient` cujo `load()` caiu nessa janela segue sem offline (`storage_error`), como com qualquer adapter. Sem Web Locks não há a quem seguir: a aba que falha fica falhando.
- `close()` durante a troca: o loop de tentativas para, o que abriu nesse meio-tempo é fechado e o lock passa ao próximo.
- `clientId` e fila são compartilhados: uma mutation de uma aba pode ser reenviada por outra no `load` (mesmo `mid`, mesmo `clientId` → dedup do servidor, roda uma vez) e o update otimista registrado por nome aparece nas duas.
- OPFS coordena por padrão (os Workers das abas elegem o dono do pool); IndexedDB/TinyBase/SQLite: `coordinateTabs({ name, open: () => indexedDbStorage({...}) })`. Sem Web Locks, cada aba lidera sozinha (comportamento anterior).
- Provado: simulação com `FakeLocks` + `BroadcastChannel` do Node (`test/tabs.test.ts`, `test/opfs.test.ts`, `test/remote.test.ts`: morte do líder com chamada em voo, líder que sai com chamada em andamento, resposta atrasada a um `id` antigo, Worker que cai depois do `load`, close gracioso, aba que não abre segue o próximo líder e volta à fila, aba sozinha que falha, `close()` durante a troca, dois `EmberClient`s) e no **Chromium real** (`test/browser/`, playwright-core + navegador já instalado; pulado sem navegador): OPFS em Worker e IndexedDB coordenado — aba A online (engine na página sobre SQLite-Wasm) lidera, aba B offline segue, o resultado local de B re-renderiza com os patches de A, mutation offline de B vai para a fila compartilhada, A fecha → o Worker de B assume os arquivos, B fecha → aba C offline acha réplica (FTS5) e fila no OPFS.

**Limites conhecidos:** mutations não rodam no cliente — escritas offline não mudam linhas da réplica, só as camadas otimistas (que se reaplicam sobre cada novo resultado local); resultados locais são reativos só até o primeiro valor do servidor (depois vale o servidor, que já é reativo); a réplica é parcial, então `take`/contagens/ranking bm25 locais podem diferir do servidor até a próxima resposta; um valor em cache montado de referências mostra cada linha na versão mais nova replicada (que pode ser mais nova que a daquele resultado); entre epochs (restore do shard) a ordem dos `applyPatch` não é conhecida: vale o último gravado até o próximo valor do servidor; identidade local = `sub`/`iss` do JWT sem verificação (tokens não-JWT → identidade guardada ou null); IndexedDB/memória/TinyBase resetam a réplica em qualquer mudança de schema (SQLite só quando o planner recusa); rowdiffs só para valores que são arrays de docs (`{page}` paginado é regravado inteiro, com referências); OPFS exige Worker de módulo e `FileSystemFileHandle.createSyncAccessHandle` (só o Chromium foi testado aqui); no OPFS o pool tem `capacity` arquivos (2 por banco: o principal + um por shard).


### Mutations no cliente (G5 do Brigade)

- `runLocalMutation(fn, args, { schema, reader, identity?, now?, random?, seed? })` (`@freecorps/ember-server`) roda o
  handler de uma `mutation(...)` pública sobre `overlayReader(replica, schema)`: as leituras veem as próprias
  escritas; `insert`/`patch`/`replace`/`delete`/`increment` validam como o engine (campos de sistema, forma do
  documento, documento inexistente → `NotFound`); `ctx.scheduler` registra os jobs sem rodar (`jobs` no retorno);
  `ctx.random` é semeado (`seed`); `ctx.storage`, `ctx.runQuery`, `ctx.runMutation`, `aggregate` e `sql` lançam
  `OfflineUnsupported`. Um handler que lança não deixa nada no overlay. Ids inseridos são locais.
- `localOptimisticUpdates({ schema, mutations, queries, identity?, onError? })` (`@freecorps/ember-offline`) devolve
  `optimisticUpdates` para o `EmberClient`, um por mutation registrada. Em cada chamada: a réplica são os documentos
  dos valores carregados das `queries` registradas (já com as mutations pendentes anteriores, na ordem); uma query só
  recebe valor otimista se, rodada sobre a réplica antes da mutation, devolve exatamente o valor confirmado (assim
  projeções, contagens e consultas sobre linhas fora da tela mantêm o valor do servidor); a mutation roda e as
  queries reproduzíveis rodam de novo. Uma mutation que falha localmente não muda nada na tela (`onError`); a resposta
  do servidor vale. Na confirmação, o valor do servidor (com os ids dele) substitui o otimista.

## Componentes (`@freecorps/ember-server` ⇄ `@freecorps/ember-runtime` ⇄ `@freecorps/ember-cli`) — PLAN §12
Um componente empacota tabelas, funções, configuração, jobs e rotas HTTP. O app instala em `ember/ember.config.ts`:
```ts
// pacote do componente
const schema = defineSchema({ tables: { counters: defineTable({ key: v.string(), value: v.number() }).index("by_key", ["key"]) } });
const { query, mutation, internalMutation, action, httpAction } = componentBuilders<typeof schema, { step: number }>();
export const counter = defineComponent({
  name: "counter", schema, config: v.object({ step: v.number() }),
  functions: { lib: { add: mutation({ args: { key: v.string() }, handler: (ctx, a) => /* ctx.db só vê "counters"; ctx.component.config.step */ 0 }) } },
  http: httpRouter().route({ path: "/hook", method: "POST", handler: hookAction }),   // montado em /<nome>/hook
  bindings: (config, installName) => [],                                              // ex.: Rate Limiting (deploy)
}).use(outroComponente, { name: "inner" });                                           // aninhado

// ember/ember.config.ts
export default defineApp().use(counter, { name: "hits", config: { step: 1 } }).use(rateLimit).use(workflows);

// ember/messages.ts (código do app)
import { components, mutation } from "./_generated/server";
export const send = mutation({ args: {...}, handler: (ctx, a) => {
  const n = ctx.runMutation(components.hits.lib.add, { key: a.channel });   // síncrono, mesma transação
  ...
}});
```
- **Composição, não runtime separado.** `composeApp({ schema, functions, app, http })` produz **um** schema e **um** mapa de funções antes de qualquer coisa rodar (Worker, codegen, deploy):
  - tabela física `<install>$<tabela>` (aninhado: `email$rateLimit$<tabela>`), id prefix `<install>$<prefix>`, e os `v.id("<tabela>")` dos documentos do componente reescritos para o nome físico. Um `v.id` num documento de componente só pode citar tabelas do próprio componente: `v.id` de tabela do app (ou de outro componente, ou um nome com erro de digitação) é recusado no `composeApp` com erro claro — o componente não conseguiria ler esse id (`db.get` → `ValidationError`) e args `v.id` com esse nome nunca validariam; ids do app ficam em `v.string()` (opacos para o componente, como `userId` no `push`). `$` nunca é válido num nome de tabela do app, então não colide;
  - funções `@<install>/<módulo>:<fn>` (aninhado: `@email/@rateLimit/lib:x`). Nomes de funções do app não podem começar com `@` nem `&`;
  - `manifest.components = { "<install>": { component, tables: { lógica: física }, httpPrefix, bindings? } }` — só existe quando há componentes, então o hash (versão de schema) de apps sem componentes não muda.
  - Por isso migrações (`ADD COLUMN`, recusas), índices staged/backfill, agregados, FTS, índices externos (bindings `EMBER_VEC__<tabela com $→_S_>__<índice>`), o catálogo de shards, o `_ember/data` do painel e a reatividade funcionam sem código novo. **As tabelas de um componente existem em todo shard, ao lado das do app**: uma chamada roda no shard e na transação de quem chamou (componentes não declaram `shards` nem `.shard()`).
- **Escopos.** O escopo de uma função vem do nome (os segmentos `@x/`). No engine (`ComponentScopes`):
  - `ctx.db` aceita só nomes lógicos das tabelas do próprio escopo; `db.get/patch/replace/delete` de um id de outro escopo → `ValidationError`; `normalizeId` → null. O app não lê tabelas de componentes e vice-versa.
  - `ctx.db.sql` num componente cita nomes lógicos; o engine prefixa CTEs `"<lógica>" AS NOT MATERIALIZED (SELECT * FROM "<física>")` (fundidas com um `WITH [RECURSIVE]` do próprio statement). No app, a allowlist é só das tabelas do app.
  - Validação de args/retorno com `v.id("t")` usa os nomes lógicos do escopo da função.
  - `ctx.component = { name: "<install path>", config }` nas funções de componente (ausente no app).
- **Chamadas.** `QueryCtx.runQuery`, `MutationCtx.runQuery/runMutation` (novos) são **síncronos** (D6) e rodam na transação de quem chamou: query aninhada grava no mesmo read set (reatividade atravessa a fronteira); mutation aninhada roda num savepoint — se lançar, as escritas, mudanças e jobs dela são desfeitos e o erro sobe (o chamador pode capturar). Profundidade máxima 32. Em actions, `ctx.runQuery/runMutation/runAction` e `ctx.scheduler` seguem as mesmas regras de resolução (cada chamada é uma transação, como antes).
- **Resolução de referências** (`resolveReference(escopo, ref)`): `"mod:fn"` = função do próprio escopo; `"@filho/mod:fn"` = função **pública** de um filho direto (internas e netos → `FunctionNotFound`); `"&<nome absoluto>"` = *function handle* (`createFunctionHandle(ref)` no app), que qualquer escopo pode chamar ou agendar — é como um componente chama de volta o app (callbacks, passos de workflow). Componentes são código confiável instalado pelo app; handles não são capacidades contra código hostil.
- **Clientes nunca chamam funções de componente:** `engine.functionInfo("@x/...")` devolve `visibility: "internal"` e `component: "x"`; WS e HTTP respondem `FunctionNotFound`, e o `ActionRunner` recusa `@x/...` sem `internal`.
- **Agendamento:** `ctx.scheduler.runAfter(ms, "lib:fn")` dentro de um componente resolve relativo ao escopo; o job grava o nome absoluto (`@x/lib:fn`) e roda no escopo do componente. Jobs de action de componente vão para a mesma `EMBER_ACTIONS`. Crons do app podem apontar para funções de componente.
- **Ganchos (hooks)** — `defineComponent({ crons, queues, email })`:
  - `crons: (config, installName) => cronJobs({ shard })... | CronDef[]`: `fn` relativo ao componente e só funções do próprio escopo (senão erro na composição). Viram crons com nome `@<install>/<nome>` e `fn` absoluto, ao lado dos do app (`resolvedCrons`, System DO, um Cron Trigger por minuto; o codegen os põe em `manifest.crons`).
  - `queues: { <nome>: { binding?, shard?, consumer?, handler(ctx, batch) } }` (nome `[a-z][a-z0-9-]*`, até 20): uma fila `ember-<project>-<env>-<install>-<nome>` por instalação (`/` e `_` viram `-`), binding de producer `EMBER_Q_<INSTALL>_<NOME>` (ou `binding`, que não pode repetir entre instalações). No manifesto: `components[key].queues = [{ name, queue: sufixo, binding, consumer? }]`. O deploy cria a fila antes do upload, liga o binding, adiciona o Worker como consumer (com `consumer`: `batch_size`, `max_wait_time_ms`, `max_retries`, `retry_delay`) depois, guarda os nomes em `.ember/component-queues.json` e apaga (desliga o consumer, depois a fila) as que saíram do app; `ember destroy` apaga todas. O `queue()` do Worker reconhece a fila pelo nome (`EMBER_PROJECT`/`EMBER_ENV`) e entrega o **lote inteiro** ao handler, como uma action no escopo do componente (`ctx.component`), no shard `shard(config)` (padrão `global:main`); o handler dá `ack`/`retry` por mensagem; exceção → `retryAll()` (o que já tinha ack fica). `ember dev`: produtor e consumer locais (`ember-<project>-local-...`).
  - `email: { match?(to, config), shard?, handler(ctx, message) }`: o `email()` do Worker (Email Routing) vai para o primeiro componente instalado cujo `match` aceita o destinatário (sem `match` = todos); nenhum → `setReject("Address not found")`. `message` é o `ForwardableEmailMessage` (`from`, `to`, `headers`, `raw`, `rawSize`, `setReject`, `forward`, `reply`). Exceção no handler sobe do `email()` (o Email Routing não aceita a mensagem; o remetente vê falha temporária).
  - Novo tipo de `ComponentBinding`: `{ type: "send_email", name, destination_address?, allowed_destination_addresses?, allowed_sender_addresses? }` (binding do Email Service; no `ember dev`, o Miniflare simula o envio).
- **HTTP:** `httpRouter().route({ path | pathPrefix, method, handler: httpAction(...), shard? })` em `ember/http.ts` (novo: o Ember não tinha roteador) e em componentes (montados em `httpPrefix`, padrão `/<install>`). O Worker tenta as rotas depois dos próprios endpoints (`/ws`, `/health`, `/api/query|mutation|action`, `/api/storage/*`, `/api/_ember/*`) e antes de `/api/auth/*` e do 404; caminho exato antes de prefixo (o mais longo); método errado → 405. Rotas dentro dos caminhos reservados são recusadas na definição/montagem. O httpAction roda com um `ActionCtx` no escopo da rota, no shard `route.shard` (string ou função do request; padrão `global:main`); `ctx.auth` vem de um bearer válido, e token ausente ou inválido roda anônimo (webhooks mandam os próprios headers). Exceção → 500 sem detalhes (logado) e ponto de métrica `http:<METHOD> <path>`.
- **Codegen:** `ember/ember.config.ts` e `ember/http.ts` são arquivos reservados (não são módulos de função) e entram no entry do Worker (`createEmberWorker({ schema, functions, crons, auth, app, http })`). O `manifest.json` leva o schema composto e as funções de componente (`component: "<install>"`). `api.d.ts`/`dataModel.d.ts` continuam só do app e sem imports (cliente). `_generated/server` exporta `components` tipado como `ComponentsApi<typeof app>` (só código de servidor): nome errado de componente/função, args errados, função interna do componente e query usada como mutation são erros de tipo.
- **Deploy:** `bindings` pedidos pelos componentes vão para a metadata do Worker. Hoje: `{ type: "ratelimit", name, limit, period: 10 | 60 }` → binding `ratelimit` com `namespace_id` = 31 bits do sha256 de `ember-<project>-<env>/<binding>` (estável por ambiente; dois bindings com o mesmo id dividiriam contadores por local).
- **Offline:** `runLocalQuery` não tem os componentes: `ctx.runQuery` → `OfflineUnsupported` (cai no cache).

**Componentes oficiais**
- `rateLimit` (`@freecorps/ember-rate-limit`, pacote próprio como o `@convex-dev/rate-limiter`: opcional e sem pesar no `ember-server`). Tabela `rateLimits(name, key, value, ts)` com `by_name_key`. *Token bucket* (`rate` por `period` ms, contínuo, `capacity` padrão `rate`) e *fixed window* (`rate` por janela alinhada a `start`, padrão a época; sobra acumula até `capacity`). `lib:limit` é mutation: dentro de uma mutation do app, consumo e escrita do app commitam juntos (falhou depois → tokens devolvidos); recusa não escreve nada; `reserve` permite ficar negativo (até `maxReserved`) e devolve quando a reserva vale; `throws` lança `RateLimited` com `data: { name, retryAfter }`. `lib:check`/`lib:getValue` são queries (reativas), `lib:reset`. Config por chamada (o helper `RateLimiter` manda a config de cada limite) ou nomeada na instalação (`config.limits`). O limite é exato **por shard**; um limite global entre shards usa um shard escolhido (`ctx.onShard`). Opcional: `config.binding` pede um Rate Limiting binding da Cloudflare e `edgeLimit(ctx, nome, chave)` o consulta em actions/HTTP — aproximado e por local (documentação da Cloudflare), para cortar abuso antes do shard, não para cotas.
- `workflows` (`@freecorps/ember-workflows`). **Decisão: componente sobre o scheduler do shard, não Cloudflare Workflows.** Pesquisa (docs.cloudflare.com, 2026-11): Workflows têm passos `step.do` com retries, `sleep` até 365 dias, `waitForEvent` (timeout padrão 24 h), 10k passos (até 25k), resultado de passo ≤ 1 MiB, 300 criações/s por conta, retenção de 7–30 dias, e o provisionamento é um recurso por conta (`PUT /workflows/<nome>` + binding `workflow`). Por que o scheduler é mais sólido no Ember: (1) **começar é atômico com a mutation** (`workflow.start(ctx, ...)` é uma escrita + um job na mesma transação; `create()` de um Workflow é I/O, proibido em mutation pelo D6 — exigiria outbox); (2) **passos de query/mutation rodam exatamente uma vez**, na mesma transação da entrada do diário (num Workflow o passo é at-least-once e a escrita no shard seria outra transação); (3) o estado vive no shard do workflow, então `status` é uma query **reativa** (UI ao vivo) e cai no catálogo/painel/PITR do shard; (4) funciona igual no `ember dev` e nos testes, sem recurso extra na conta e sem limite de criação por conta; (5) o scheduler já dorme anos (encadeamento de 30 dias). Custo: replay do handler a cada passo (O(n²) em passos; `maxSteps` padrão 1000) e vazão limitada à do shard. Cloudflare Workflows pode virar um backend alternativo (driver num `WorkflowEntrypoint`) se aparecer necessidade de dezenas de milhares de passos ou de passos com CPU longa.
  - API: `const workflow = new WorkflowManager(components.workflows)`; `export const onboard = workflow.define({ args, handler: async (step, args) => ... })` (o driver: uma internalAction exportada pelo app); `step.runQuery/runMutation/runAction(ref, args, { name?, retry? })`, `step.sleep(ms)`, `step.sleepUntil(t)`, `step.waitForEvent(evento, { timeoutMs? })`; `workflow.start(ctx, internal.mod.onboard, args, { onComplete?, context? })`, `status`, `steps`, `sendEvent`, `cancel`, `cleanup`.
  - Laço: `lib:start` (mutation, na transação de quem chama) → `lib:drive` (action: carrega o diário, roda o driver do app via handle — replay: passos do diário resolvem com o resultado gravado, o primeiro passo novo suspende o handler) → `lib:advance` (mutation, cercada pelo índice do passo): query/mutation executadas **ali**, na mesma transação do diário; action → job `lib:runAction` (at-least-once, retry com backoff por `retry`; padrão sem retry, ou `defaultRetry`) → `lib:actionDone`; sleep → job `lib:wake` em `ctx.now + ms`; evento → consome um evento já enviado (buffer na tabela `events`) ou espera `lib:sendEvent` (timeout → `lib:wake`). Fim (`completed`/`failed`/`canceled`) grava status/resultado e chama o `onComplete` (handle) na mesma transação; um `onComplete` que lança é desfeito e logado.
  - Todo job leva o índice do passo; jobs duplicados ou velhos (actions são at-least-once) não fazem nada. Diário que não bate com o código (tipo/nome do passo na mesma posição) → `failed` com `NonDeterminism`, mesmo se o handler capturar o erro. Um driver que não é de `workflow.define` (qualquer handle passa no `start`) e devolve algo que não é passo do índice atual, `done` ou `failed` → `failed` com `InvalidOutcome` (nunca fica `running` sem job). Passos em paralelo (`Promise.all`) ainda não são suportados (o primeiro passo novo suspende).
  - Tabelas: `workflows`, `steps` (`by_workflow`, `by_event`), `events`.
- `push` (`@freecorps/ember-push`): além dos helpers de tabela e do `sendPush` (API inalterada), `pushComponent` + `PushNotifications`: tabela `devices` no componente, `register/unregister/devices/tokens`, `send` (mutation: agenda a entrega na transação de quem chama — "notificar quando a mensagem for gravada" fica atômico), `sendNow` (action). A entrega roteia **por device**: token Expo → Expo Push (`EXPO_ACCESS_TOKEN`, nome configurável; recibos após `receiptsDelayMs`, padrão 15 min, pendentes rechecados até 3 vezes); token nativo → APNs/FCM direto (`config.apns`/`config.fcm`, segredos do env), lacrado quando o device tem chave (`config.encryption`). Poda tokens mortos, limpa VoIP mortos e grava o ambiente APNs descoberto (`lib:applyResults`). Contrato em "Push direto e E2E" abaixo.
- **`files` e `auth` continuam embutidos (decisão).** `files`: `_files` é uma tabela de sistema do shard e o refcount acontece no engine em **qualquer** escrita com `v.file()` — inclusive em tabelas de componentes —, junto com endpoints `/api/storage/*`, eventos R2 e bucket/fila do deploy; como componente, precisaria de ganchos em toda escrita de todo escopo, sem ganho. Componentes usam `v.file()` e `ctx.storage` normalmente (o storage é do shard, compartilhado). `auth`: o Better Auth roda num DO `Auth` próprio (D8) e `ctx.auth` é verificado no Worker antes de qualquer shard; não é um conjunto de tabelas de shard. A identidade de quem chamou é propagada para as funções de componente (`ctx.auth`), diferente do Convex.
- `email` (`@freecorps/ember-email`): ver "Email".

## Email (`@freecorps/ember-email`, `/cloudflare`, `/schema`) — PLAN §16

O Ember entrega as peças (componente e onboarding de domínio). O produto — API HTTP estilo Resend, chaves de API, inbox, app móvel, SDK — fica em [freecorps/mail](https://github.com/freecorps/mail) e não faz parte deste contrato.

```ts
// ember/ember.config.ts
export default defineApp().use(email, { config: { domains?, rateLimit?: { rate, period, capacity? }, hooks?: { onInbound?, onEvent? }, shard?, transport?: "binding" | "rest", binding?: "EMAIL", maxAttempts?: 5, spamPerHour?: 20, maxInboundBytes?, storeRaw?, layout? } });
const email = new Email(components.email);
email.send(ctx, { from, to, cc?, bcc?, replyTo?, subject?, html?, text?, headers?, attachments?: [{ filename, contentType, file }], template?: { name, data }, tags?, idempotencyKey?, sendAt?, project? });
```
- **Estado num shard só** (`config.shard`, padrão `global:main`): as filas e o `email()` escrevem lá, então quem chama `send` roda nesse shard. Tabelas (`email$<t>`): `emails`, `events`, `suppressions`, `templates`, `mailboxes`, `threads` (agregado `unread`: `count` e soma de `unreadCount` por mailbox), `messages` (`searchIndex("search")` em `searchText` = assunto + remetente + texto, filtros `mailbox`, `direction`); componente aninhado `rateLimit`.
- **Envio:** `lib:send` é mutation (atômica com quem chama). Ordem: idempotência por `(project, idempotencyKey)` (devolve o primeiro `{id, status, duplicate: true}`; sem expiração) → validação (endereços estritos, ≤ 50 destinatários, assunto ≤ 998, headers fora de `from/to/cc/bcc/subject/reply-to/content-*`, sem CR/LF) → supressões do projeto (destinatários suprimidos saem e nunca ficam num campo entregue; todo `to` suprimido → os `cc` restantes viram o `to`; `bcc` nunca é promovido, então sem `to` nem `cc` → `status: "suppressed"`, nada é enviado nem conta no limite) → `rateLimit` por projeto (token bucket; recusa → `RateLimited`, sem escrita) → linha `queued`/`scheduled` + job `lib:deliver` em `sendAt`. As supressões são checadas de novo quando a entrega reivindica o email (`lib:claim`): um endereço suprimido enquanto o email esperava (agendado ou em backoff) sai dos destinatários pela mesma regra, e se não sobrar `to` o email vira `suppressed` sem ser enviado. `cancel` (só `scheduled`/`queued`), `retry` (só `failed`), `sendBatch` (até 100, tudo ou nada).
- **Entrega** (`lib:deliver`, action at-least-once): `lib:claim` (mutation) passa `queued|scheduled → sending` e conta a tentativa; job duplicado ou velho não reenvia. Template guardado renderizado na entrega; anexos lidos do `files`. Transporte: binding `send_email` (`env.EMAIL.send({...})` → `{ messageId }`) ou REST (`POST /accounts/{id}/email/sending/send`). Códigos permanentes (`E_SENDER_NOT_VERIFIED`, `E_VALIDATION_ERROR`, `E_RECIPIENT_SUPPRESSED`, ..., REST 4xx menos 429 e menos os códigos transitórios `E_SENDER_DOMAIN_NOT_AVAILABLE`/`E_RATE_LIMIT_EXCEEDED`) → `failed`; transitórios → de volta a `queued` com backoff `30 s·2^(n-1)` (máx. 1 h) até `maxAttempts`. `E_HEADER_*`: reenvia sem os headers recusados (primeiro mantém `In-Reply-To`, `References` e `X-*`; depois nenhum) e grava `droppedHeaders`. Cron do componente `@email/sweep` (10 min): `sending` há mais de 10 min vira `failed` com `E_DELIVERY_UNKNOWN` (nunca reenvia às cegas; `retry` manual).
- **Eventos:** fila do componente `events` (`ember-<project>-<env>-email-events`) ← assinatura de eventos do Email Service (`source: { type: "email.sending", zone_id, domain }`, `destination: { type: "queues.queue", queue_id }`). Cada lote é uma mutation `lib:applyEvents`: dedup por `eventId` (redelivery soma `duplicates`), status só avança (`sent < delivery_delayed < delivered < bounced|failed < complained`), evento antes do `finish` é aplicado quando o envio é gravado, bounce `hard` e `complained` → supressão do projeto, `hooks.onEvent` na mesma transação. Mensagem que não é evento → `ack` e log.
- **Inbound** (gancho `email`): tamanho > `maxInboundBytes` (padrão 25 MiB) ou endereço sem mailbox → `setReject`. Roteamento: endereço da mailbox, `+tag` mantido (`support+t_<token>@`). `.eml` e anexos (até 50; o resto contado) vão para `files` quando há `EMBER_FILES`; parse com `postal-mime`; DKIM/DMARC/SPF do primeiro `Authentication-Results` cujo authserv-id é `mx.cloudflare.net`. `lib:ingest` (mutation): dedup por `(mailbox, Message-ID)`; thread por (1) token do plus-address (de qualquer remetente), (2) `In-Reply-To`/`References` só com DMARC `pass` e remetente = contato da thread, (3) mesmo contato + assunto normalizado, thread aberta, ≤ 30 dias; nova thread ganha número sequencial por mailbox e token aleatório; > `spamPerHour` mensagens do remetente na última hora → thread `spam`; nova mensagem reabre `waiting`/`closed`. Auto-resposta (mailbox `autoReply`, `{{subject}}`, `{{number}}`, `{{name}}`): só em thread nova, nunca para `Auto-Submitted`/`Precedence: bulk|list|junk|auto_reply`/`List-Id`, `no-reply@`/`mailer-daemon@` ou spam, com `Auto-Submitted: auto-replied` e `Reply-To` com o token; roda num savepoint e falha (limite etc.) não perde a mensagem. `hooks.onInbound` recebe `{ threadId, messageId, mailbox, number, newThread, status, from, subject, snippet, autoSubmitted }` num savepoint: exceção é logada e desfeita, a mensagem fica.
- **Inbox:** `threads` (paginado por mailbox e status), `thread`, `unread` (agregado), `search`, `reply` (de `mailbox.address`, `Reply-To` com token, `In-Reply-To`/`References` da última inbound, citação, thread → `waiting`), `note`, `markRead`, `markUnread`, `setStatus`, `assign({ threadId, assignee | null, assigneeName? })` (grava `threads.assignee`), `compose({ mailbox, to, cc?, subject, text, html?, author? })` (conversa nova a partir da mailbox: thread com número e token, respostas entram nela pelo token) e `recent({ mailboxes, threads? })` (últimas threads com as mensagens, para réplicas offline). `@freecorps/ember-email/schema` exporta só `emailSchema` (tabelas, sem postal-mime) para o cliente compor a réplica local.
- **Templates:** motor próprio (`{{x}}` escapado, `{{{x}}}` cru, `#if/else`, `#unless`, `#each` com `@index`; ausente = vazio), `emailLayout` (tabelas, estilos inline, cor só hex) e `htmlToText`. Escolha: templates são dados no shard (editáveis pela API), renderizam em qualquer lugar sem dependências; React Email exigiria React no bundle e JSX em build — quem quiser renderiza numa action e passa `html`.
- **Domínios (`@freecorps/ember-email/cloudflare`):** sem armazenamento nem HTTP; só `fetch` (roda no Worker, Node e Bun). `CfCreds = { accountId, apiToken, fetch? }`; `resolveAccountId(token, { env? })` (= `CLOUDFLARE_ACCOUNT_ID` ou a única conta do token; senão erro claro); `emailResources(project, env, install = "email") → { worker: "ember-<project>-<env>", eventsQueue: "ember-<project>-<env>-<install>-events" }`.
  - `syncDomain(c, { name, enableRouting?, sending?, receiving? }, { prev, mailboxes, worker, queue }) → DomainState` (idempotente; rode de novo até `status: "verified"`). Envio: `POST /zones/{z}/email/sending/subdomains {name}` (+ registros de `.../dns`; a Cloudflare gerencia o DNS). Recebimento só é **verificado** — apex precisa do Email Routing `ready`, subdomínio precisa estar em `email/routing.subdomains`; `enableRouting` cria o subdomínio (`POST /email/routing/dns {name}`) só quando pedido, porque não há API para removê-lo (o único `DELETE` desliga a zona inteira). Uma regra literal por endereço de `mailboxes` do domínio → `worker` (nunca muda uma regra que aponta para outro destino: vira nota). Assinatura de eventos `email.sending` (zona + domínio) → `queue` quando o envio está habilitado. Domínio fora das zonas da conta → `status: "failed"` com nota.
  - `DomainState = { name, zoneId?, zoneName?, sendingTag?, status: "pending" | "verified" | "failed", sending, receiving, routingStatus?, records: DnsRecord[], ruleIds, subscriptionId?, createdSending?, notes }`: quem chama guarda (tem os ids do que foi criado) e devolve em `prev` e em `destroyDomain`.
  - `destroyDomain(c, state) → string[]` apaga as regras, a assinatura e o domínio de envio só se foi criado pelo onboarding; 404 conta como apagado; outros erros voltam na lista (o chamador mantém o estado para tentar de novo).
  - Peças soltas também exportadas: `findZone`, `sendingDomain`, `ensureSending`, `deleteSending`, `routingState`, `enableRoutingSubdomain`, `ensureWorkerRule`, `deleteRule`, `ensureEventSubscription`, `deleteEventSubscription`, `isDomainName`, `CfError { status, codes }`.
- **Exemplo:** `examples/email-lite` (só o componente + rotas admin mínimas) é o app que o E2E publica.

## Push direto e E2E (`@freecorps/ember-push` ⇄ `@freecorps/ember-react-native` ⇄ `@freecorps/ember-expo-push`) — PLAN §10, R12
- **Transporte por device**, decidido pelo registro: `provider` `expo` (token `ExponentPushToken[...]`), `apns` (hex, com `environment` `sandbox|production`) ou `fcm`. Omitido → inferido do token (`inferPushProvider`). Linha do device (`pushDevicesTable`, também a tabela do componente): `userId, token, provider, platform?, deviceName?, environment?, voipToken?, publicKey?, updatedAt`; os campos novos são opcionais (sem migração). `registerPushDevice` recusa `environment` fora de `sandbox|production` e `publicKey` que não seja ponto P-256 não comprimido (65 bytes, base64url).
- **APNs** (`sendApns`): `POST https://api[.sandbox].push.apple.com/3/device/<token>`, `authorization: bearer <ES256 JWT {iss: teamId, iat}, kid: keyId>` reusado por 40 min (por isolate), `apns-topic` (bundle id; VoIP `<bundle>.voip`), `apns-push-type` `alert|background|voip`, `apns-priority` (5 para `low` e background, senão 10), `apns-expiration` (`0` = uma tentativa), `apns-collapse-id` (≤ 64 bytes). Corpo: `aps` (alert title/subtitle/body, sound, badge, thread-id, category, content-available, mutable-content, interruption-level) e os dados do app em `body` (onde o expo-notifications lê). `ExpiredProviderToken` → assina de novo e repete uma vez. Device sem ambiente: host padrão, e o outro depois de `BadDeviceToken` (o ticket diz o `environment` que funcionou).
- **FCM** (`sendFcm`): JWT RS256 da conta de serviço (`scope firebase.messaging`, `aud` = `token_uri`, `exp` ≤ 1 h) trocado por access token (cache até 5 min antes de expirar; trocas concorrentes compartilhadas; 401 → troca de novo uma vez); `POST https://fcm.googleapis.com/v1/projects/<project_id>/messages:send` com `{ message: { token, notification?, data: { body: JSON(data) }, android: { priority HIGH|NORMAL, ttl "<s>s", collapse_key?, notification: { channel_id, sound, tag, notification_count }? } } }`. TTL ≤ 28 dias.
- **Urgência** (`PushMessage.urgency`): `low` (APNs 5, FCM NORMAL, TTL 4 h), `normal` (padrão: 10, HIGH, 1 h), `high` (10, HIGH, 15 min, `time-sensitive`) — os valores do relay do Brigade (README dele). `ttl` explícito ganha (0..30 dias). Retries: 429/5xx/erro de rede, 2 vezes com backoff, `Retry-After` respeitado.
- **Erros → poda:** `DeviceNotRegistered` (APNs `Unregistered`/`ExpiredToken`/410, `BadDeviceToken`; FCM `UNREGISTERED`) e `InvalidToken` (token malformado) → device apagado (VoIP: só o `voipToken` é limpo). `MismatchSenderId` (topic, `SENDER_ID_MISMATCH`), `InvalidCredentials`, `InvalidArgument` (FCM `INVALID_ARGUMENT`), `MessageTooBig`, `MessageRateExceeded`, `ProviderNotConfigured`, `RequestFailed` → mantido.
- **Envelope E2E** (`sealPushContent`; portado do `packages/push` do Brigade, MIT): HPKE RFC 9180 modo base, DHKEM(P-256, HKDF-SHA256) + HKDF-SHA256 + AES-128-GCM, `info = "freecorps.ember push v1"`, sem AAD. Texto claro: JSON `{ title?, subtitle?, body?, data?, iat }` ≤ 2048 bytes. Envelope `{ v: 1, k, enc, ct }` (base64url sem padding; `k` = base64url dos 6 primeiros bytes de SHA-256 da chave pública, `enc` = ponto efêmero não comprimido). Mudar suite, `info` ou formato exige mudar os três lados (WebCrypto no servidor, noble no JS, CryptoKit no NSE) e subir `v`.
  - APNs: `aps.alert` = fallback (texto ou `title-loc-key`/`loc-key`), `mutable-content: 1`, `ember: <envelope>`; nada do conteúdo em claro.
  - FCM: só `data` = `{ ember: JSON(envelope), urgency, fallbackTitle?, fallbackBody?, channelId?, tag? }` (sem `notification`).
  - `encryption`: `off`; `auto` (padrão: lacra se o device é `apns`/`fcm` e tem `publicKey`); `required` (sem chave, ou Expo → só o fallback, sem `data`). Só pushes com algo visível são lacrados; background/VoIP vão como estão em `auto` e perdem `data` em `required`. Ficam em claro por desenho: fallback, prioridade, TTL, collapse id/tag, thread id, categoria, badge, som, `k`.
- **Cliente** (`@freecorps/ember-react-native`): `registerForPush({ kind: "device", publicKey?, androidChannels?, categories?, environment? })` → `{ token, provider: "apns"|"fcm", platform, environment? (iOS), publicKey? }`; `pushEnvironment()` lê `expo.extra.emberPush.apsEnvironment` (`development` → `sandbox`, `production` → `production`).
- **Device** (`@freecorps/ember-expo-push`): plugin Expo grava `extra.emberPush = { apsEnvironment, appGroup, keychainService, keyName }`; `aps-environment` = `development` local, `production` com `EAS_BUILD` (override `apsEnvironment`/`EMBER_APS_ENVIRONMENT`). Chave: item do expo-secure-store (iOS: generic password, service `<keychainService>:no-auth`, account `<keyName>`, access group = App Group, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`) com `{ "v": 1, "keys": [{ "d", "pub" }] }` (atual primeiro; rotação guarda uma anterior). NSE (`EmberNotificationService`, iOS 17+ para abrir; senão fallback) lê `EmberPushAppGroup`/`EmberPushKeychainService`/`EmberPushKeyName` do próprio Info.plist, troca título/subtítulo/corpo e põe `data` em `userInfo.body`. Android: tarefa `ember-push-decrypt` (`registerTaskAsync`) abre e agenda notificação local no `channelId`, id = `tag`; falhou → fallback (nunca silêncio).
- **Segredos:** `APNS_KEY` (texto do `.p8`), `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_TOPIC` (ou `config.apns.topic`), `FCM_SERVICE_ACCOUNT` (JSON), nomes configuráveis; lidos do env na hora do envio. Definidos com `ember env set` (secrets de Worker de `ember-<project>-<env>`, mantidos pelo deploy); `.dev.vars` no `ember dev`. APNs exige HTTP/2: funciona do Worker publicado, não do workerd local.


## Embutir o runtime num Worker existente (G4 do Brigade)

Para um app que já tem seu Worker e faz deploy com Wrangler (sem `ember deploy`). O contrato abaixo é estável: os
nomes de binding e de variável não mudam sem nota de versão.

**Entrada do Worker.** O módulo de entrada exporta as classes de DO do Ember ao lado das suas e monta o runtime sob
um prefixo:

```ts
import { createEmberWorker } from "@freecorps/ember-runtime";
export { Shard, System } from "@freecorps/ember-runtime";
const ember = createEmberWorker({ schema, functions, crons, basePath: "/ember", auth: { verify } });
export default {
  fetch: (req, env, ctx) => (ember.handles(req) ? ember.fetch(req, env, ctx) : myApp.fetch(req, env, ctx)),
  queue: (batch, env, ctx) => (batch.queue.startsWith("ember-") ? ember.queue(batch, env, ctx) : myApp.queue(batch, env, ctx)),
  scheduled: async (c, env, ctx) => { await myApp.scheduled(c, env, ctx); await ember.scheduled(c, env, ctx); },
};
```

- `basePath` (`"/ember"`): o runtime atende `/ember/ws`, `/ember/api/query|mutation|action`, `/ember/api/storage/*`,
  `/ember/api/_ember/*`, `/ember/health` e as rotas HTTP do app e dos componentes sob o prefixo; fora dele, `fetch`
  responde 404 e `handles(request)` é `false`. O cliente usa a URL com o prefixo: `new EmberClient({ url:
  "https://app.example.com/ember" })`. As URLs de arquivo assinadas (modo proxy) são relativas ao runtime
  (`/api/storage/get?…`, que `client.files` junta à `url` do cliente, prefixo incluído); com `EMBER_PUBLIC_URL` (só a
  origem) são absolutas e levam o prefixo (`https://app.example.com/ember/api/storage/get?…`).
- **Auth:** o hook `auth.fetch` recebe a requisição como o navegador mandou, com o prefixo, para o Better Auth ver a
  URL pública (callbacks, redirecionamentos, caminho do cookie). Configure o componente de auth com
  `basePath: "/ember/api/auth"`. O resto do runtime vê os caminhos sem o prefixo.
- `createEmberWorker` precisa rodar no módulo de entrada antes de qualquer `Shard`/`System` acordar (ele registra a
  config que os DOs leem).
- `handles(request)` é para o roteamento do Worker hospedeiro.

**Bindings** (`wrangler.jsonc` do app):

| Binding | Tipo | Obrigatório | Para quê |
|---|---|---|---|
| `SHARD` | Durable Object `Shard` (SQLite: `new_sqlite_classes`) | sim | os shards |
| `SYSTEM` | Durable Object `System` (SQLite) | com crons | crons com fuso |
| `EMBER_ACTIONS` | Queue (produtor e consumidor, nome `ember-…`) | não | action jobs (sem ela, rodam no alarm do shard) |
| `EMBER_FILES` | R2 | com `ctx.storage` | bytes dos arquivos |
| `EMBER_IMAGES` | Images | não | miniaturas |
| `EMBER_REGISTRY` | D1 | não | catálogo/painel (`ember deploy` cria; embutido, opcional) |

**Variáveis e segredos:** `EMBER_PROJECT`, `EMBER_ENV` (nomes nos logs, métricas e catálogo; `EMBER_ENV=local` em
desenvolvimento), `EMBER_STORAGE_SECRET` (assina as URLs de arquivo no modo proxy), `EMBER_PUBLIC_URL` (origem
pública, para URLs absolutas), `EMBER_ADMIN_TOKEN` (`/api/_ember/*`), `EMBER_R2_*` (presign S3 do R2, opcional),
`EMBER_LOCATION_HINT`, `EMBER_METRICS`/`EMBER_METRICS_SAMPLE`, `EMBER_TRACE` (opcionais).

**Migrações de schema** rodam no primeiro wake de cada shard, como com `ember deploy`. O que o `ember deploy`
provisionaria (a Queue de actions, o catálogo D1) entra no `wrangler.jsonc` à mão; catálogo e painel são opcionais.
