# Auth E2E on Cloudflare production (`ember init --auth` → `ember deploy --wait`)

Run on 2026-11-04 (about 19:20 UTC) against the FreeCorps account (`<ACCOUNT_ID>`), using only
`https://ember-spike-auth-e2e-dev.<subdomain>.workers.dev`.

- **Resources.** One Worker, `ember-spike-auth-e2e-dev` (project `spike-auth-e2e`, env `dev`), plus its three SQLite DO
  namespaces (`Shard`, `System`, `Auth`). Nothing else was created. The Worker was deleted at the end (see Cleanup).
- **Project.** A throwaway directory in `/tmp`. Its `node_modules/@ember/*` were symlinks to `packages/*`, and it had a
  `package.json` so that `npx ember` ran `packages/cli/bin/ember.js`. The steps were `npx ember init --auth`, then
  `npx ember deploy --env dev --wait`. The sample includes:
  - `auth.config.ts` with `emailAndPassword` and `organization()`;
  - `users.ts` with `me`, `addCredits`, the sensitive `spendCredits` and `internal.users.sync`;
  - a `profiles` table.
- **Client.** The same macOS laptop in Campinas, running Node 24 `fetch` (keep-alive). Requests went to the edge at
  **GIG**.
- **Secrets.**
  - The Cloudflare token came from the CLI's wrangler fallback and was never printed.
  - `EMBER_AUTH_SECRET` was generated by `ember deploy` and sent once as `secret_text`. Its value was never displayed.
  - Credentials of the test user (random email at example.com, random password) lived only in the E2E process's memory.
  - The admin token for `--wait` was random and different for each deploy.
- **Bundle.** 2,292 KiB unminified (Better Auth plus the Ember runtime).

## What the first deploy did

```
deploy ember-spike-auth-e2e-dev: create (new DO classes: Shard, System, Auth)
  bundle 2291.6 KiB
  auth: https://ember-spike-auth-e2e-dev.<subdomain>.workers.dev (EMBER_AUTH_SECRET generated now)
  uploaded ember-spike-auth-e2e-dev (created Shard, System, Auth)
  cron triggers: * * * * *
  auth: embedded the JWKS (1 key) as EMBER_AUTH_JWKS
waiting for shards to migrate ...
  shards ready: global:main
```

The deploy took 17 s end to end, including codegen, bundling, upload, workers.dev, the JWKS secret and `--wait`. It was
one multipart Script PUT with these settings:
- `exports` containing `Shard`, `System` and `Auth`;
- bindings `SHARD`, `SYSTEM` and `AUTH`;
- the `nodejs_compat` flag;
- `EMBER_AUTH_URL` as `plain_text`, set to the workers.dev URL, which was resolved before the upload;
- `EMBER_AUTH_SECRET` as `secret_text`;
- `keep_bindings: ["secret_text", "secret_key"]`.

After that, the CLI fetched `GET /api/auth/jwks`, which made the Auth DO create its EdDSA key, and stored the result with
`PUT /workers/scripts/<w>/secrets` (`EMBER_AUTH_JWKS`). **That secret PUT creates a new deployment by itself.** The
deployments list showed 3 entries after the redeploy: create, JWKS secret, code-only.

## E2E results over HTTPS (all checks passed)

The latencies below are client wall-clock times, which include about 38 ms of RTT to the edge (keep-alive `/health`:
p50 38 ms, min 31 ms over 11 calls). No `locationHint` was set.

| Step | Status | Latency |
|---|---|---|
| `GET /api/auth/jwks` (first call, cold Auth DO) | 200, 1 EdDSA key | 719 ms |
| `POST /api/auth/sign-up/email` (scrypt in the Worker) | 200 | 538 ms |
| `POST /api/auth/sign-in/email` | 200, session token (`set-auth-token`) | 494 ms |
| `GET /api/auth/token` (mint JWT) | 200, 3-part JWT | 200 ms |
| query `users:me` with the JWT: `ctx.auth` subject = user id, `claims.email` = email, synced profile present | 200 | 678 ms (profile visible 678 ms after sign-in, at the first poll) |
| query anonymous → `null`; invalid token → 401 | 200 / 401 | 291 / 200 ms |
| query with the opaque session token (Auth DO lookup path) | 200 | 327 ms |
| mutation `users:addCredits` (JWT) | 200 → 10 | 342 ms |
| **sensitive** mutation `users:spendCredits` (JWT, session checked in the Auth DO) | 200 → 7 | 332 ms |
| warm query `users:me` (JWT verified in the Worker), n=10 | 200 | p50 303, min 291, max 353 ms |
| warm mutation `addCredits`, n=10 | 200 | p50 311, min 305, max 361 ms |
| warm **sensitive** mutation `spendCredits`, n=10 | 200 | p50 320, min 307, max 341 ms |
| `GET /api/auth/get-session` (bearer), n=5 | 200 | p50 180, min 173, max 229 ms |
| `GET /api/auth/token`, n=5 | 200 | p50 178, min 168, max 227 ms |
| `POST /api/auth/sign-in/email`, n=3 (spaced by the 3/10 s rate limit) | 200 | p50 506, min 482, max 607 ms |
| `POST /api/auth/sign-out` | 200 | 444 ms |
| **sensitive mutation after sign-out with the same, unexpired JWT** | **401 `unauthenticated`** | 456 ms |
| non-sensitive mutation after sign-out with the same JWT | 200 (expected: the JWT is valid until `exp`, 5 min) | 343 ms |
| `get-session` with the signed-out token | 200, `null` | 229 ms |

Reading the numbers:
- **Shard round trip.** Shard calls cost about 300 ms against 38 ms for the Worker alone. Placement dominates: the Shard
  DO landed far from GIG (see R8).
- **Sensitive check.** Calls to the Auth DO alone (get-session, token) take about 180 ms. The sensitive check adds about
  10 ms at p50 over a plain JWT mutation (320 vs 311 ms), because the Worker's verify-by-session-id RPC to the Auth DO
  overlaps the shard warm-up.
- **Sign-in.** Sign-in costs about 500 ms. Of that, roughly 90 ms is scrypt in the Worker (R7), plus two DO hops: the
  credential lookup, then the sign-in itself.

## Second, code-only deploy (`keep_bindings` validation)

A new query (`users:ping`) was appended and `ember deploy --env dev --wait` was run again:

```
deploy ember-spike-auth-e2e-dev: code-only
  auth: https://ember-spike-auth-e2e-dev.<subdomain>.workers.dev (EMBER_AUTH_SECRET kept from the previous deploy)
  uploaded version <id> (#3)
  deployed <id>@100%
  cron triggers: * * * * *
  shards ready: global:main
```

The deploy took 16.6 s. The version upload carried no `EMBER_AUTH_SECRET` and no `EMBER_AUTH_JWKS` binding; both were
inherited through `keep_bindings`. The JWKS step was skipped because the secret already existed.
