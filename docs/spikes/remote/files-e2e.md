# Files E2E on Cloudflare production (PLAN §7)

Run on 2026-11-04, around 19:50–20:05 UTC, on the FreeCorps account (`<ACCOUNT_ID>`). The project was `spike-files`,
env `e2e`, so every resource was named `ember-spike-files-e2e*`. The client was a Node 24 laptop in Campinas using the
real `@ember/client` (`client.files.upload`).

- **Project.** A throwaway directory in `/tmp`, with `node_modules/@ember/*` symlinked to `packages/*`. Its parts:
  - `ember.json` with `"resources": { "files": true }` (later also `"images": true`) and
    `environments.e2e.vars.EMBER_FILES_GC_GRACE_MS = "20000"`, so GC could be watched without waiting 24 h;
  - schema `photos { title, file: v.file() }`;
  - `storage:generateUploadUrl` (mutation → `ctx.storage.generateUploadUrl(args)`), `storage:meta`;
  - `photos:add/remove/url` (`url` = `ctx.storage.getUrl` after the app's own check);
  - `thumbs:make` (action, `ctx.images`).
- **Mode: proxy.** The deploy token is the wrangler OAuth fallback, which may not create API tokens
  (`GET /accounts/:id/tokens` → 9109). So `ember deploy` could not mint bucket-scoped S3 credentials and none were
  provided, and it deployed in proxy mode:
  - uploads go to `PUT /api/storage/put|part` on the Worker, which checks the upload token against the shard and calls
    `bucket.put` / multipart through the R2 binding;
  - downloads go to `GET /api/storage/get` with an HMAC-signed, expiring query.

  **The presigned-S3 path was not exercised remotely** (see Gaps).
- **Secrets.**
  - The Cloudflare token came from the CLI's wrangler fallback and was never printed or written.
  - `EMBER_STORAGE_SECRET` was generated by `ember deploy` (`secret_text`, kept on re-deploys) and never displayed.
  - The `--wait` admin token was random per deploy. On the first run it was briefly written to a 0600 temp file, deleted
    right after; later runs kept it in the environment only.
  - Upload tokens and URL signatures are redacted below. Local logs that held them were deleted.

## Deploy

First deploy (29.6 s end to end, including `--wait`):

```
deploy ember-spike-files-e2e: create (new DO classes: Shard, System)
  bundle 224.7 KiB
  files: proxy mode (no S3 credentials: set EMBER_R2_ACCESS_KEY_ID/EMBER_R2_SECRET_ACCESS_KEY for presigned URLs)
  files: bucket ember-spike-files-e2e (created), queue ember-spike-files-e2e-files (created)
  uploaded ember-spike-files-e2e (created Shard, System)
  cron triggers: none
  files: consumer added, event notifications configured
ember-spike-files-e2e → https://ember-spike-files-e2e.<subdomain>.workers.dev
  shards ready: global:main
```

The deploy made these calls, in order:
1. `POST /r2/buckets`.
2. `PUT /r2/buckets/:b/cors`: GET/PUT/HEAD, headers `*`, `ETag` exposed.
3. `PUT /r2/buckets/:b/lifecycle`: `t/` expires after 7 days; multipart uploads abort after 7 days.
4. `POST /queues`.
5. Script PUT. Bindings: `EMBER_FILES` (r2_bucket), `EMBER_R2_BUCKET`, `EMBER_R2_ACCOUNT_ID`, `EMBER_PUBLIC_URL`,
   `EMBER_STORAGE_SECRET`.
6. `POST /queues/:id/consumers`: the Worker as consumer.
7. `PUT /event_notifications/r2/:b/configuration/queues/:id`: rules `f/` and `t/` for
   `PutObject`, `CopyObject` and `CompleteMultipartUpload`.

Read back from the API: both notification rules, both lifecycle rules (`ember-abort-multipart`,
`ember-expire-temp-uploads`), and the consumer `{script: ember-spike-files-e2e, type: worker}`.

**Bug found and fixed (16d0ed2).** The second deploy failed with
`[11020] Event notification R2 rule conflict ... invalid overlap`. The notification API reports `queueId` as a dashed
UUID (`25378711-c158-...`), but the Queues API returns it undashed (`25378711c158...`). Because of that mismatch the
idempotency check missed the existing rules and re-PUT them. Ids are now compared without dashes, and a regression test
was added. After the fix, the third deploy logged `files: consumer ok, event notifications ok` and created nothing.

nobody references is collected after the grace period, counted from its creation. In production the grace is 24 h.

# Second run: presigned (S3) mode

Run on 2026-11-04, around 20:09–20:12 UTC, same account. The project was `spike-files`, env `s3`, so every resource was
named `ember-spike-files-s3*`.

- **Credentials.** An R2 API token was provided by the user as two secret files. Each file was read only inline, in the
  `ember deploy` command: `EMBER_R2_ACCESS_KEY_ID="$(cat …)" EMBER_R2_SECRET_ACCESS_KEY="$(cat …)"`.
  - `ember deploy` uploaded them as `secret_text` and logged only `files: presigned R2 URLs (S3 credentials provided)`.
  - The E2E script never saw them. It used only the tickets and URLs the Worker signed.
  - Credentials, signatures and the account host are redacted here (`<acct>.r2.cloudflarestorage.com`).
- **Deploy.** It created the bucket, CORS, lifecycle, queue, consumer and notifications exactly as in the first run.
